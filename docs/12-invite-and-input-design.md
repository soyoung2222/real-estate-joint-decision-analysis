# 초대·입력 설계 — 위치 기반 구조를 사용자 기반으로 옮기기

*2026-08-19*
`04-benchmarks.md`의 **“서비스 이름이 아니라 빌려올 메커니즘으로”** 를 위밋플레이스에 실제로 적용한 기록.
참조를 가져올 때 무엇이 딸려 오는지까지 본다.

---

# 1. 구조 대조

| | 위밋플레이스 | 우리 |
|---|---|---|
| 후보를 | **생성한다** — 지도 전체가 후보 공간 | **판정한다** — 관심매물 5개 고정 |
| 조건이 | **1개** (위치) | **여러 개** (위치·예산·면적·주차) |
| 두 사람의 값이 | **같은 종류** — 둘 다 출발지 | **다른 종류 가능** — A는 통근, B는 면적 |
| 계산 방향 | **역방향** — 조건을 만족하는 지점을 찾음 | **순방향** — 주어진 지점을 평가 |
| 답이 | **하나의 최적 지점** | 판정 3분류. 최적 없음 |
| 입력 인터랙션 | **2~3회** | **7~10회** |

**세 번째가 결정적 차이다.** 위밋은 A·B가 같은 축에 값을 내므로 “중간”이 계산된다.
우리는 A가 통근 40분, B가 면적 66㎡를 내는데 **이 둘의 중간은 존재하지 않는다.**
그래서 위밋의 *계산*은 가져올 수 없고, *구조*만 가져올 수 있다.

---

# 2. 추상화하면 동형이다

```
위밋:  각자의 개인값(출발지) → 공통 공간(지도)    에 투영 → 겹침 → 후보
우리:  각자의 개인값(조건)   → 공통 공간(매물 5개) 에 투영 → 겹침 → 판정
                                      ↑
                              여기만 다르다
```

투영할 공통 공간이 **지도냐 매물 목록이냐**만 다르다.
`decisions/0003`(조건은 사람에 저장)이 이 구조의 전제이고, 위밋은 그 전제가
국내에서 이미 작동한다는 증거다.

---

# 3. 가져오는 것

## ① 투영 은유 — ② 조건 입력 화면

각자의 값이 공통 공간에 그려지고, 겹치는 곳을 본다.

```
A 강남역 40분 ▓▓▓▓▓
B 여의도 40분    ░░░░░
겹치는 곳        ███       ← 여기에 관심매물 5개를 얹는다
                  ● ●  ●
```

- 위밋의 **시각 언어**를 쓰되 후보는 **기존 관심매물**이다 (생성하지 않음)
- **`조건 모순` 예외가 그림 하나로 설명된다** — 겹치는 영역이 없으면 즉시 보임
- 숫자로는 감이 안 오는 “통근 40분”을 **아이소크론**으로 이해시킨다

## ② 입력 최소성 — 상대는 “자기 것”만 낸다

위밋에서 B는 출발지 하나만 낸다. 후보를 고르지도, 판단하지도 않는다.
우리도 같다 — **B는 매물을 담지 않고 자기 조건만 낸다.**
이미 설계에 있던 원칙이고, 위밋이 그 근거가 된다.

## ③ 결과의 즉시성

중간 확인 단계나 “제출” 버튼이 없다. 입력이 끝나면 바로 결과다.

---

# 4. 가져오면 안 되는 것 — 구조에 딸려 오는 것들

## ① 거리 합산 ⚠️ 가장 위험

위밋의 중간지점은 두 사람 이동시간의 **합 또는 최대값을 최소화**한 결과다.
**그게 곧 집계다.**

```
위밋:   min( A거리 + B거리 )        →  Additive Utilitarian
   또는  min( max(A거리, B거리) )    →  Least Misery
```

거리 구조를 가져오면서 이 계산이 따라 들어오면 `decisions/0001` 위반이다.
**우리 통근 조건은 각자의 임계값이지 합이 아니다.**

> **금지** — `A 34분 + B 22분 = 56분`, `평균 28분`, `합계 이동시간` 같은 값을
> 화면·계산·정렬 어디에도 만들지 않는다.

`07-tradeoff-patterns.md`에서 정리한 집계 전략이 **여기로 몰래 들어온다.**
참조를 가져올 때 가장 조심할 지점이다.

## ② 하나의 최적해

위밋은 “가장 공평한 지점”을 낸다. 단일 최적 개념이 있다.
우리가 그러면 총점이고, 05번에서 정리한 함정 ②(“우리 둘에게 **가장 좋은** 집”)로 되돌아간다.

## ③ 후보 생성

위밋은 지도에서 새 장소를 찾는다. 우리는 찾지 않는다 (G5 — 탐색으로 안 넓힌다).

## ④ 지도를 판정의 중심에 두기

**통근은 조건 4개 중 하나일 뿐이다.** 면적·주차는 지도에 그려지지 않는다.
지도를 메인으로 만들면 **위치가 다른 조건보다 중요해 보인다** — 강조 차등이라 G10 위반.

```
지도    위치 조건 전용 보조 화면 — ②에서 입력을 이해시키는 용도
판정    여전히 조건별 표 — ⑤
```

# 5. 입력 개수 격차 — 2~3회 vs 7~10회

이 격차가 H1의 실제 마찰이다. 위밋의 “하나 넣으면 끝”을 그대로 흉내 낼 수는 없지만,
**첫 결과까지의 거리**는 좁힐 수 있다.

## 채택: 점진적 공개 (progressive disclosure)

```
1단계   출근지 + 예산                →  즉시 판정
                                        "5개 중 3개가 예산·통근 안에 들어옵니다"
2단계   "더 좁히시겠어요?"            →  필수 조건 ①
3단계   결과를 보고 필요하면          →  필수 조건 ②
```

**입력 2개로 이미 결과가 나온다.** 근거가 셋이다.

| 근거 | 내용 |
|---|---|
| H3 완화 설계 | `01-hypotheses` — *“온보딩에서 한꺼번에 묻지 않는다. 출근지는 통근 시간을 볼 때, 대출 조건은 실질 비용을 볼 때 받는다”* |
| G8과 충돌하지 않음 | 필수 슬롯 2개는 **상한**이지 처음부터 채우라는 뜻이 아니다 |
| 위밋의 감각 | 최소 입력으로 결과를 본 뒤 다듬는 흐름 |

## 대안과 비교

| 안 | 방식 | 판정 |
|---|---|---|
| **점진적 공개** | 2개 → 결과 → 추가 | **채택** — 첫 결과까지 가장 짧다 |
| 프리셋 기본값 | 필수조건에 흔한 값을 미리 선택 (“통근 40분 이하”) | **보조로 채택** — 단계마다 기본값을 두면 탭이 줄어든다 |
| 전부 한 화면 | 4개를 한 번에 | 기각 — 부담이 커 보이고 **이탈 지점을 못 잰다** |
| 대화형 입력 | 챗봇처럼 순차 질문 | 보류 — 탭 수는 비슷한데 구현 비용이 큼 |

## 이 결정이 바꾸는 것

| 문서 | 변경 |
|---|---|
| 14번 화면 ② | `4단계 순차` → **`2단계 필수 + 2단계 선택 확장`** |
| 15번 KPI | 완주율을 **2개 완료 / 3개 / 4개**로 나눠 측정 — 어디까지 채우는지가 H3의 실제 답 |
| `08-edge-cases` | **“필수 조건 0개 상태의 판정”** 이 새 경로로 추가됨 ↓ |

## 새로 생긴 예외 — 필수 조건 없이 판정하기

1단계(출근지+예산)만으로 판정할 때는 **필수 조건이 없다.**
판정 3분류가 성립하려면 비교할 조건이 있어야 하는데, 예산과 통근만으로도
`둘 다 충족 / 한쪽만 / 둘 다 불충족`은 나온다 — **예산은 공통, 통근은 각자**이기 때문이다.

```
1단계 판정 가능 조건
  예산      가구 총액 → A·B 상한이 다르므로 한쪽만 충족이 나올 수 있다
  통근시간  각자 다른 출근지 → 한쪽만 충족이 나올 수 있다
```

**즉 1단계만으로도 Hero Feature가 작동한다.** 이게 점진적 공개를 채택할 수 있는 진짜 이유다.
다만 통근 임계값을 안 받았으므로 1단계에서는 **충족/미충족이 아니라 실제 값만** 보여주고,
필수 조건이 들어온 뒤에 판정으로 전환한다.

| 단계 | 통근 표시 |
|---|---|
| 1단계 (임계값 없음) | `A 34분 · B 22분` — 값만 |
| 2단계 이후 (임계값 있음) | `A 34분 ≤ 40분 ✓` — 판정 |

# 6. 위밋플레이스 실사용 때 잴 것

`10-cjm-opportunity-score.md` §3의 R1을 이 문서 기준으로 구체화한다.

| 측정 항목 | 왜 |
|---|---|
| 링크를 열고 입력을 끝낼 때까지 **탭 수** | Tier 0 카톡(3초)과 비교할 유일한 수치 |
| **가입을 요구하는 시점** — 있는가, 결과 전인가 후인가 | 우리 로그인 위치 결정 (F5 — 관심매물 조회에 로그인 필요) |
| 출발지 입력 UI — 검색인가 지도 탭인가 | ② 화면 |
| **결과를 총점으로 주는가 후보로 주는가** | 가져오면 안 되는 것 ①·② 확인 |
| 아이소크론을 실제로 그리는가 | ② 지도 표현의 실현 가능성 |
| 한 명만 입력했을 때 화면 | **우리 `B 대기 중` 빈 경로의 직접 참조** |
| 상대가 안 들어오면 어떻게 되나 | 동일 |

**마지막 두 줄이 특히 중요하다.** 위밋도 우리와 같은 문제(상대가 안 들어옴)를 갖고 있고,
어떻게 처리하는지가 `decisions/0002`의 1인 빈 경로 설계에 직접 쓰인다.

# 7. 정리 — 참조를 가져오는 절차

이번 사례에서 실제로 쓴 순서다. 다른 참조 서비스에도 같은 절차를 쓴다.

```
1. 구조를 대조한다            무엇이 같고 무엇이 다른가
2. 추상화해서 동형인지 본다    같으면 구조를 가져올 수 있다
3. 가져올 것을 고른다          은유 · 원칙 · 흐름
4. 딸려 오는 것을 찾는다  ★    계산 방식 · 최적 개념 · 범위 확장
5. 우리 결정과 충돌하는지 본다  decisions/ · 가드레일
6. 실사용 때 잴 것을 정한다     숫자로 남을 것
```

**4번이 이 절차의 핵심이다.** 좋아 보이는 것만 고르면 그 밑에 깔린
계산 방식이 같이 들어온다. 위밋의 경우 **거리 합산**이 그것이었다.
