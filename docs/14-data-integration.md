# 데이터 연동 — 네이버 사이에 끼는 방식

*2026-08-19*
우리는 매물 데이터를 **읽고, 판정하고, 파라미터로 돌려보낸다.** 쓰지 않는다.

---

# 1. 위치

```
                    네이버 부동산
                         │
      ① 관심매물 목록 조회 │ ② 매물 상세 (판정에 쓸 필드만)
                         ▼
              ┌─────────────────────┐
              │    우리 레이어       │   조건 저장 · 판정 · 양보 문장 · 완화
              │   화면을 온전히 그림  │   ← 저장하는 건 우리 데이터뿐
              └─────────────────────┘
                         │
      ③ 검색 결과 수 조회  │ ④ 필터 파라미터 넘기기
                         ▼
                  네이버 부동산 검색
```

**매물 데이터에 쓰기(write)를 하지 않는다.** G5(탐색·매물 DB를 만들지 않는다)가 지켜지는 방식이다.

## 링크 파싱을 쓰지 않는 이유

초안에서 “매물 URL을 공유 시트로 받아 파싱”을 검토했다. 그건 **별도 앱 전제의 잔재**이고,
네이버 안 기능으로 확정된 지금은 맞지 않는다.

| | 링크 파싱 | API 조회 |
|---|---|---|
| URL 구조가 바뀌면 | **깨진다** | 무관 |
| 받는 데이터 | 페이지 전체를 긁어야 함 | **필요한 필드만** |
| 화면 통제 | 부분적 | **온전히 우리 것** |
| 로그인 | 사용자 세션에 의존 | 정식 권한으로 |

> **혼동 주의** — 여기서 말하는 것은 **A의 관심매물 조회**다.
> **B에게 보내는 초대**는 여전히 **링크(기본) + 코드(보조)** 이고 성격이 다르다.
> 하나는 내부 데이터 접근, 하나는 사람 간 전달이다.

# 2. 필요한 것 넷

## ① 관심매물 목록 조회

| | |
|---|---|
| 무엇 | 매물 ID 리스트 (+ 저장 시각) |
| 언제 | A가 “같이 고르기”를 시작할 때 (A-02) |
| 권한 | **로그인 필요** — 개인 데이터 (F5) |
| 주의 | B는 이걸 호출하지 않는다. B는 **A가 만든 후보 묶음**을 본다 |

## ② 매물 상세 — 판정에 쓸 필드만

**전부 받지 않는다.** 판정에 쓰는 것만 받는다.

| 필드 | 쓰는 곳 |
|---|---|
| 주소 · 좌표 | 통근·역도보 계산, 식별 |
| 보증금 · 월세 · 관리비 | 실부담 환산 (`03-cost-model`) |
| 전용면적 · 방 개수 | 하한형 조건 |
| 준공연도 | 건물 연식 (상한형) |
| 주차 · 엘리베이터 | 유무형 조건 ✓ 확인됨 (F4) |
| **역 도보 시간 · 최근접역** | 상한형 조건 ✓ 확인됨 (F4) |
| 층수 | 반지하·1층 배제 |
| 거래 상태 | 소진 감지 (A-16j) |

**사진·설명·중개사 정보는 받지 않는다.** 판정에 쓰지 않고, 사진은 평가적 조건화 위험이 있다(G10).

## ③ 검색 결과 수 조회 — “이 조건으로 매물 34개”

재탐색 제안(A-13b-2)에서 **필터를 걸기 전에** 결과 수를 보여주기 위한 것이다.

```
필터 조건  →  count 조회  →  "이 조건으로 매물 34개"
                              0~3개면 "조건이 아니라 필터가 문제"라는 신호
```

| 판단 | 내용 |
|---|---|
| 왜 필요한가 | 적용 전에 판단할 수 있고, **너무 좁은 필터를 미리 알려준다** |
| 정확한 수가 필요한가 | 아니다. **근사치도 충분**하다 — “약 30여 개”, “100개 이상” |
| 부하가 크면 | 디바운스 + 근사치. 실시간 정확도보다 **응답 속도가 중요**하다 |
| 0개면 | **제안 자체를 하지 않는다.** 어느 조건이 0을 만드는지 짚어준다 |

## ④ 필터 파라미터 넘기기

우리 조건을 네이버 검색 필터로 변환해 **URL 파라미터로 넘긴다.** 자동으로 걸지 않고
사용자가 `[ 이 필터로 찾아보기 ]`를 눌러야 적용된다 (G1 — 필터도 결정이다).

| 조건 | 넘기나 | 변환 |
|---|---|---|
| 예산 | ✅ | 두 사람 중 **더 낮은 상한** |
| 전용면적 · 방 개수 | ✅ | 더 **높은 하한** |
| 건물 연식 · 역세권 | ✅ | 더 **짧은 쪽** |
| 주차 · 엘리베이터 | ✅ | 한 명이라도 필요하면 필요 |
| **통근시간** | ❌ | **출근지가 각자 달라 필터 하나로 표현 불가** ↓ |
| 거래유형 · 매물유형 | — | 우리 조건이 아니다. 사용자가 건 것을 유지 |

### 통근을 못 넘기는 문제

검색 결과를 받아 우리가 직접 통근 필터링을 할 수도 있지만 **하지 않는다.**

- 매물을 대량으로 받아야 해서 무겁고
- 그 순간 우리가 **탐색을 만드는 것**이 되어 G5와 충돌한다

대신 조건이 사람에 저장돼 있어 **새 매물을 담는 순간 자동 판정된다**(A-20b).
필터는 1차로 좁히는 도구일 뿐이고, 정밀 판정은 담은 뒤에 한다.

> 화면 문구 — “통근 조건은 저장돼 있어서, 새로 담는 매물에 바로 적용됩니다.”

# 3. 우리가 저장하는 것

**매물 데이터는 저장하지 않는다.** 우리 것만 저장한다.

| 데이터 | 소속 | 근거 |
|---|---|---|
| 출근지 · 예산 · 필수조건 · 선호 · 확인항목 | **사람** | `decisions/0003` |
| 후보 묶음 (매물 ID 5개 + 공유 상태) | **프로젝트** | B가 보는 공유 객체 |
| 판정 결과 · 미달량 · 양보 문장 | **계산 결과** | 저장 안 해도 되지만 캐시 가능 |
| 현장 확인 기록 · 유지/보류/제외 | **매물** | `decisions/0003`. **단계 2에서 보존 문제 발생** → `13-screen-inventory` |

# 4. 경로 API 호출량

통근 시간은 매물 데이터에 없다. **출근지 × 매물 좌표**로 계산해야 하고,
회차가 2~3번 반복되므로(H5) 누적을 봐야 한다.

## 호출이 발생하는 지점

**통근 시간은 `(출근지, 매물좌표, 이동수단)`의 함수다.** 이 셋이 안 바뀌면 값도 안 바뀐다.
여기서 무엇이 호출을 만들고 무엇이 안 만드는지가 갈린다.

| 사건 | 호출 | 이유 |
|---|---|---|
| 후보 5개 담기 (A만) | **5** | 매물이 새로 들어옴 |
| B 조건 입력 완료 | **5** | 출근지가 하나 더 생김 |
| 매물 1개 추가 | **2** | A용 + B용 |
| 출근지 변경 | **5** | 그 사람 것만 전부 |
| 이동수단 변경 | **5** | 동일 |
| **조건 완화 (임계값 조정)** | **0** ★ | **통근 시간은 안 변한다.** 40분→50분은 판정 기준만 바뀜 |
| 예산·면적 조건 변경 | **0** | 경로와 무관 |
| 재진입 · 화면 이동 | **0** | 캐시 |
| 매물 소진 | **0** | 빼기만 함 |

**조건 완화가 0회라는 게 크다.** F6은 가장 많이 조작될 화면인데
슬라이더를 아무리 끌어도 경로 호출이 없다 — 미달량 계산은 이미 가진 값으로 한다.

## 여정 전체 추정 — 1쌍 기준

```
회차 1   후보 5개 담기 (A)              5
         B 진입 + 조건 입력             5
         출근지 변경 1회 (가정)          5
         매물 2개 추가 (가정)            4
회차 2   새 후보 5개                   10
회차 3   새 후보 5개                   10
                                     ────
                                      39회 / 쌍
```

**가정** — 회차 3번(H5의 총 방문 4.1곳 기준), 출근지 변경 1회, 매물 추가 2개.
출근지 변경과 매물 추가는 실측이 없어 **보수적으로 잡은 값**이다.

| 시나리오 | 호출/쌍 |
|---|---|
| B 미참여 (H1 실패) | **약 20** — 역설적으로 절반 |
| 기본 | **39** |
| 회차 4번 + 잦은 조건 변경 | 55~60 |

## 효율화 — 순서대로 적용

| # | 방법 | 절감 | 확실성 |
|---|---|---|---|
| 1 | **결과 캐시** `(출근지, 매물좌표, 이동수단) → 시간` | 재진입·완화 시 **0회** | ✅ 확실 — 위 표가 이미 반영 |
| 2 | **좌표 그리드 반올림** (100m 격자) | 같은 단지 매물이 1회로 | ⚠️ 후보에 같은 단지가 얼마나 섞이는지 **측정 필요** |
| 3 | **전역 캐시** `(출근지 역, 그리드)` | 인기 조합 재사용 | ⚠️ 히트율 **측정 필요** |
| 4 | **지연 계산** — 담을 때 말고 판정 화면 진입 시 | 담고 안 보는 경우 | ⚠️ 점진적 공개는 “입력 2개 후 즉시 결과”를 약속했으므로 **거기서는 못 미룬다** |

**2번이 생각보다 클 수 있다.** 관심매물은 비슷한 지역에 몰리기 마련이고,
아파트 단지면 여러 매물이 같은 좌표다. 다만 **얼마나 몰리는지는 실측해야 한다.**

**3번은 출근지가 역 단위일 때 효과가 크다.** 강남역·여의도역 같은 상위 출근지가
반복되면 `(강남역, 흑석동 그리드)` 조합은 여러 쌍이 공유한다.

## 규모 감

SOM 시나리오(6.7만~20.1만 명 = 3.4만~10.1만 쌍)를 대입하면:

| | 여정 전체 | 월 환산 (여정 2.5개월) |
|---|---|---|
| 캐시 1번만 | 131만 ~ 392만 | **52만 ~ 157만** |
| 2·3번까지 (30% 절감 가정) | 92만 ~ 274만 | 37만 ~ 110만 |

> **주의** — SOM 자체가 가정 시나리오다(`06-team-brief` §5).
> 이 숫자는 **자릿수 감각**이지 예측이 아니다. 30% 절감도 가정이다.

| | |
|---|---|
| 이동수단 | 대중교통 / 자차 — 사용자가 고른 것으로 |
| 실패 시 | **미충족이 아니라 `계산 불가`** (`08-edge-cases` 원칙) |
| 역 도보 | **매물 데이터에 있으므로 계산하지 않는다** (F4, 2026-08-19 확인) |

# 4-1. 외부에는 매물 API가 없다 — 전제가 확인됐다

2026-08-19 조사 결과 **네이버 부동산은 공식 오픈 API를 제공하지 않는다**(F20).
외부 서비스가 매물을 받으려면 크롤링뿐이고, 그건 약관·안정성 양쪽에서 쓸 수 없다.

> **따라서 “네이버 안 기능”은 선택이 아니라 필수 전제다.**
> 별도 앱 안을 초기에 검토했다가 접었는데, 그 판단이 사후에 근거를 얻었다.

| 프로토타입은 어떻게 하나 | |
|---|---|
| 실제 매물 데이터 | **못 받는다** |
| **H1 선행 측정** | **더미 데이터로 충분** — 조건 대조 없이 목록 공유 + O/X 반응만 재기 때문 |
| 국토부 실거래가 API | 무료지만 **거래 완료 데이터**이고 주차·EV·역도보 필드가 없다(F21) |

**H1이 프로토타입 없이도 측정 가능하다는 설계가 여기서 값을 한다.**

# 4-2. 대중교통 경로는 두 층으로 갈린다

초안에서 “네이버 Directions가 자동차 중심이라 대중교통 계산 수단이 불확실하다”고
리스크를 잡았다. **걱정을 잘못 잡았다.**

```
내가 본 것    네이버 Directions(외부 공개 API)가 자동차 중심
실제 전제     우리는 "네이버 안 기능"이다
              → 네이버 지도의 대중교통 길찾기 엔진을 쓰면 된다
              → 외부 API 제약은 애초에 우리 얘기가 아니었다
```

| 층 | 수단 | 상태 |
|---|---|---|
| **역기획 대상** (네이버 내부 구현) | 네이버 지도 대중교통 엔진 | ✅ 문제 없음 |
| **팀 프로토타입** | **ODsay LAB Basic** — 일 1,000 호출 무료(F25) | ✅ **하루 25쌍** 분량. 사용자 테스트에 넉넉 |
| 실서비스 규모 | 월 52만~157만 호출 | 대용량 협의 필요 — **네이버 내부면 무관** |

프로토타입 계산: 1쌍당 39회 ÷ 일 1,000 = **하루 25쌍**.
H1 선행 측정은 경로 계산이 **아예 없고**(목록 공유 + O/X만), H3 입력 테스트도 소규모라
무료 쿼터로 충분하다.

> **주의** — ODsay 무료 API는 도보 구간을 **직선거리로 계산**한다.
> 우리는 역 도보를 매물 데이터에서 받으므로 대부분 무관하지만,
> 통근 시간에 포함된 도보 구간에는 오차가 생긴다.

# 5. 확인이 필요한 것

전부 **네이버 내부 사정**이라 우리가 정할 수 없다.

| 항목 | 왜 중요한가 |
|---|---|
| 관심매물 조회 API의 존재·권한 | ①이 안 되면 후보를 못 담는다 — **제품의 전제.** 2026-08-19 확인: **외부에는 공식 API가 없다**(F20) |
| ~~대중교통 경로 API~~ | ✅ **해소** — 네이버 내부에는 지도 대중교통 엔진이 있고, 프로토타입은 ODsay로 대체 가능(F25). §4-2 |
| **공유 객체를 비로그인으로 열 수 있는가** | B의 로그인 시점을 뒤로 미룰 수 있는지가 여기 달림 (`13-screen-inventory`) |
| 검색 count 조회 가능 여부·부하 | ③이 안 되면 결과 수 미리보기를 뺀다 |
| 검색 필터 URL 파라미터 규격 | ④의 구현 방식 |
| 경로 API 호출 비용·쿼터 | 회차 반복까지 고려하면 호출량이 누적된다 |

**두 번째가 가장 크다.** H1 깔때기에서 로그인 위치가 여기서 정해진다.
