## 기기 전제 — A는 PC 웹, B는 링크 ✅ 결정

초안은 모바일 뷰를 전제로 그렸다. **접근 경로를 보면 그렇지 않다.**

| 경로 | 마찰 |
|---|---|
| 네이버페이 **앱** | 부동산이 **하단 네비바에 작게** 들어 있어 진입 자체가 눈에 안 띈다 |
| **웹** | 검색해서 들어가야 하지만, **일단 들어오면 화면이 넓다** |

```
A (초대자)   PC 웹 우선     후보 고르기·조건 입력·판정 확인은 정보 밀도가 높다
B (수신자)   기기 무관      카톡 링크로 들어오므로 모바일일 확률이 높다
```

**A와 B의 기기가 다를 가능성이 높다.** 따라서 화면을 둘로 나눠 설계한다.

| 화면 | 기준 |
|---|---|
| A-02 후보 선택 · A-13 후보 목록 · A-14 상세 판정 · A-15 완화 | **PC 웹 우선** — 좌우 비교와 슬라이더+결과 동시 표시가 필요 |
| B-01~B-05 초대 진입 · 조건 입력 · 첫 결과 | **모바일 우선** — 카톡에서 열린다 |

**아이소크론 폐기는 유지한다.** 화면이 넓어져도 폐기 근거의 절반(위치를 다른 조건보다
과대 강조 — G10)은 그대로이고, 후보가 5개 고정이라 공간을 볼 이유가 없다는 것도 변하지 않는다.

## 매물 스냅샷 저장 ✅ 결정

매물이 빠지면 즉시 제외하지만, **그 매물의 정보와 판정까지 사라지면 안 된다.**
담는 시점에 판정에 쓴 필드를 **스냅샷으로 저장**한다.

```
저장 대상   주소 · 가격 · 전용면적 · 방 개수 · 준공연도 · 주차 · EV · 역 도보 · 좌표
            + 그때의 판정 결과와 양보 문장
            + 방문 후 현장 기록
```

| 왜 필요한가 | 내용 |
|---|---|
| **여정이 2~3개월이다** | 매물은 계속 빠지는데 비교 이력이 남으면 “이런 조건이면 이 가격이더라”는 감각이 쌓인다 |
| **현장 기록이 딸려 사라진다** | `decisions/0003`은 현장 확인 항목을 매물에 저장한다. 매물이 사라지면 방문 기록도 사라진다 |
| **조건을 바꿨을 때 재계산** | 과거 후보들이 새 조건으로는 어떻게 판정됐을지 볼 수 있다 |
| 성능 | 판정 결과를 캐시하면 재진입마다 다시 계산하지 않는다 |

> **주의** — 오래된 정보를 현재 정보처럼 보여주면 안 된다.
> `2026-08-19 기준 · 현재 거래완료`처럼 **시점과 상태를 함께 표시**한다.
> 가격은 특히 위험하다 — 스냅샷 가격을 현재가로 오인하면 판단이 틀어진다.

### 로그인을 뒤로 미룬다 ✅ 결정

초안에서는 진입 직후 로그인을 요구했다. F5(관심매물 조회에 로그인 필요)를 근거로 삼았는데,
**적용을 잘못했다.**

```
F5:  "A의 관심매물 목록" 조회에 로그인이 필요하다
       ↓
      그런데 B는 A의 관심매물 목록을 조회하는 게 아니다
      A가 고른 후보 5개를 보는 것이다
```

**A의 관심매물 목록**(개인 데이터)과 **A가 공유한 후보 묶음**(별도 객체)은 다르다.
후보를 선택하는 순간 공유 객체가 만들어지면, B는 그것을 보는 것이지 A의 계정 데이터에
접근하는 것이 아니다.

```
초대 진입 → 후보 미리보기 → 조건 입력 → 결과 확인 → [저장하려면 로그인]
                                                        ↑
                                        B가 이미 값을 본 뒤에 요구한다
```

**H1 깔때기에서 로그인이 조건 입력 뒤로 밀린다.** 지금까지 “우리가 못 고치는 구간”으로
뒀던 H1-b가 상당 부분 우리 손에 들어온다.

| 남은 제약 | 상태 |
|---|---|
| 비로그인 페이지를 만들 수 있는가 | **네이버 정책 — 우리가 정할 수 없다.** 확인 필요 |
| B가 로그인 안 하면 입력한 조건을 어디 두나 | 코드에 묶어 임시 저장? 세션? **미정** |

### 링크와 코드 — 대안이 아니라 보조 관계

| | 링크 | 코드 |
|---|---|---|
| 진입 | **클릭 한 번** | 앱·웹 진입 + 코드 입력 = 두 단계 |
| 전달 채널 | 카톡 · 문자 | **말로도 전달 가능** |
| 유실 시 | 다시 보내야 함 | **재진입 가능** |
| 선행 사례 | 위밋플레이스 | **특별시 6자리**(F3) |

**기본은 링크, 보조로 코드.** 코드 자체가 로그인을 우회하는 것은 아니다 —
우회는 위의 **공유 객체 분리**가 한다.

> **B-02가 중요하다.** 조건을 묻기 **전에** 무엇을 하는 자리인지 보여줘야 한다.
> CJM에서 B의 감정은 첫 접점부터 낮다 — 맥락 없이 입력부터 요구하면 거기서 끊긴다.

# 아직 열려 있는 질문 다섯

## ① 회차는 2~3번 반복된다 ✅ 결정

실측은 **총 방문 3.5~4.3개**(H5)인데 종료점은 2개다. 모순이 아니라 **단위가 다르다** —
2개는 “한 번 나갈 때 보는 수”, 4개는 “계약까지 총합”이다.

```
전체 여정 2.5개월 · 총 4.1곳 방문

  1회차   후보 5개 → 2개 보러 감 → 둘 다 제외 → 다시
  2회차   후보 5개 → 2개 보러 감 → 하나는 보류 → 다시
  3회차   ...
                              총 4~6곳 보고 계약
```

**우리 서비스는 한 번 쓰고 끝나는 게 아니라 2~3번 반복된다.**

| 함의 | 내용 |
|---|---|
| **재진입이 정상 경로다** | 1회차 방문 후 둘 다 제외되면 다시 담고·판정하고·정한다 (A-18c → A-20) |
| **2회차는 입력이 0번이다** | 조건이 사람에 저장돼 있어 새 매물을 담으면 **자동 판정**된다 (A-20b). `decisions/0003`의 값어치가 실제로 드러나는 지점 |
| **방문하면 조건이 바뀐다** | “생각보다 좁네”, “역세권이 이렇게 중요한 줄 몰랐네” — 조건 수정 경로가 상시 필요하다 ↓ |
| 리텐션 지표 | “재방문율”이 아니라 **“2회차 진입률”** |

### 조건 수정은 상시 접근 창 하나로 해결된다

“방문 후 조건 조정”을 별도 경로로 만들 필요가 없다. **내 조건 화면(A-19)에 언제든
들어갈 수 있으면 된다.** 진입점만 여러 곳에 둔다.

| 진입점 | 위치 |
|---|---|
| 상시 | 헤더·설정 — 어느 화면에서든 |
| 결과를 보고 | 후보 목록(A-13)에서 “내 조건 보기” |
| 막다른 길에서 | 전부 불충족(A-13b)에서 “조건 다시 보기” |
| **방문 후** | 현장 기록(A-18)에서 “조건 바꾸기” |

수정하면 **전체가 즉시 재판정**되고(A-19a 영향 미리보기), 상대에게 알림이 간다(A-19b).
회차가 반복되는 구조에서는 이 창이 **재진입의 실질적 시작점**이 된다.

## ② 선택은 비동기다 ✅ 결정

A가 고르고 며칠 뒤 B가 고를 수 있다. 처리는 **알림 + 즉시 반영**으로 한다.

| 항목 | 결정 |
|---|---|
| 선택 유효기간 | **두지 않는다** — 만료 처리라는 상태가 하나 더 생기는데 얻는 게 없다 |
| 상대가 선택하면 | **알림** — “상대가 보러 갈 집을 골랐어요” |
| **매물이 빠지면** | **즉시 제외 + 알림** — 유효기간이 아니라 **매물의 실재 여부**가 기준이다 |
| 정한 후보가 빠지면 | 한 자리가 비므로 **A-16e(남은 한 자리)로 자동 복귀** |

유효기간을 대신하는 것이 **매물 소진 감지**다. 시간이 아니라 대상이 사라지는 것이 진짜 만료다.

## ③ “합의”라는 말을 쓰지 않는다 ✅ 결정

내부 용어로만 쓴다. 화면에는 **“이번에 보러 갈 집 정하기”**.

## ④ 전부 불충족(0건)의 분기 ✅ 결정

`전부 불충족`(A-13b)일 때 길이 둘이다.

```
a)  조건 완화       기존 5개 중에서 살린다
b)  재탐색          네이버로 돌아가 새 매물을 찾는다
```

**지금까지는 a만 있었다.** 그런데 **완화를 먼저 들이대면 “네 기준을 낮춰라”가 된다.**
조건이 문제인지 후보가 문제인지를 먼저 갈라야 한다.

### 판별 — 임계선을 만들지 않고 계산으로 가른다

미달량은 조건마다 단위가 다르다(`+12분`, `−7㎡`, `+월 15만`). 이걸 비교하려고
정규화하면 **그게 곧 집계이고 `0001` 위반**이다. 그래서 **완화 시뮬레이션을 실제로 돌려본다.**

```
각 조건에 대해 "실제 미달량만큼 풀면 몇 개가 살아나는가"를 계산한다
  (완화폭은 임의값이 아니라 F6이 이미 쓰는 실제 미달량)

  1개 조건만 풀어서 살아나는 매물이 있다   →  (a) 완화 제안
  어떤 조건 하나를 풀어도 안 살아난다      →  (b) 재탐색 제안
```

**“2개를 동시에 풀면?”은 계산은 되지만 제안하지 않는다.** 조건 두 개를 낮추라는 말이
되어 G1의 편들지 않기를 넘어선다.

한 조건만 풀어서 안 살아난다는 것은 **매물마다 2개 이상의 조건을 미달한다**는 뜻이고,
그건 조건이 빡빡한 게 아니라 **후보가 안 맞는다**는 신호다.

### 화면

```
(a) 완화 가능
    "A가 역 도보를 13분까지 허용하면 2개가 살아납니다"
    "B가 전용면적을 59㎡까지 허용하면 1개가 살아납니다"
    → A-15 조건 완화

(b) 완화 불가
    "지금 후보 5개는 두 분 조건과 여러 항목에서 떨어져 있습니다.
     조건 하나를 푸는 것만으로는 살릴 수 없어요."

    [ 다른 매물 찾아보기 ]      [ 내 조건 다시 보기 ]
         → 네이버 탐색              → A-19
```

**(b)에서도 우리가 “낮추세요”라고 말하지 않는다.** 선택지만 놓는다.

### 재탐색은 “네이버 필터를 다시 거는 일”이다

여기에 중요한 사실이 하나 있다. **후보 5개는 이미 네이버 필터를 통과한 것들이다.**
사용자는 탐색할 때 거래유형·매물유형·가격·면적·단지·역세권 등으로 이미 한 번 걸렀다.

> **그런데 전부 불충족이 나왔다면, 네이버 필터와 우리 조건이 어긋나 있다는 뜻이다.**

```
네이버 필터   전세 3억 이하 · 아파트                 ← 면적 조건이 없었다
우리 조건     실부담 130만 이하 · 전용 66㎡ 이상
                                   ↑
후보 5개가 전부 면적 미달 — 애초에 66㎡ 필터를 안 걸고 찾았기 때문
```

따라서 재탐색 제안은 “다시 찾아보세요”가 아니라 **“필터를 이렇게 바꿔서 찾으세요”** 여야 한다.
선택지를 더 정확히 좁히는 것은 그쪽이다.

### 필터 제안 화면

| 조건 | 필터로 넘기나 | 어떻게 |
|---|---|---|
| 예산 | ✅ | 두 사람 중 **더 낮은 상한** |
| 전용면적 · 방 개수 | ✅ | 더 **높은 하한** |
| 주차 · 엘리베이터 | ✅ | 한 명이라도 필요하면 필요 |
| 건물 연식 | ✅ | 더 짧은 쪽 |
| 역세권(도보) | ✅ | 더 짧은 쪽 |
| **통근시간** | ❌ | **출근지가 각자 달라 필터 하나로 표현할 수 없다** |
| 거래유형 · 매물유형 | — | **우리 조건이 아니다.** 사용자가 건 것을 그대로 둔다 |

```
┌────────────────────────────────────────────┐
│  이렇게 찾으면 두 분 조건에 더 가까워요      │
│                                            │
│   지금 필터            바꿀 필터            │
│   전세 3억 이하    →   전세 3억 이하  (유지) │
│   아파트           →   아파트        (유지) │
│   면적 —           →   전용 66㎡ 이상  ← B   │
│   역세권 —         →   도보 10분 이내  ← A   │
│                                            │
│   이 조건으로 매물 34개                     │
│                                            │
│   [ 이 필터로 찾아보기 ]   [ 그냥 찾기 ]     │
│                                            │
│   ※ 통근 조건은 필터에 없지만 저장돼 있어서,  │
│      새로 담는 매물에 바로 적용됩니다.        │
└────────────────────────────────────────────┘
```

**필터를 우리가 자동으로 걸지 않는다.** 제안하고 사용자가 적용한다 —
필터도 결정이고, G1(AI가 고르지 않는다)이 여기까지 적용된다.
`[ 그냥 찾기 ]`를 나란히 두는 이유이기도 하다.

### 결과 수 미리보기 ✅ 채택

`이 조건으로 매물 34개` — 아고다·에어비앤비의 `(+34)` 패턴이다. 채택 이유가 셋이다.

| 이유 | 내용 |
|---|---|
| **적용 전에 판단할 수 있다** | 34개면 넉넉하고 2개면 너무 좁다는 것을 눌러보기 전에 안다 |
| **필터가 과한지 알려준다** | 0~3개가 나오면 **조건이 아니라 필터가 문제**라는 신호 |
| 이미 있는 계산이다 | 네이버 검색 결과 수는 별도 계산이 아니다 |

**0개일 때는 제안 자체를 하지 않는다.** “이 필터로 찾으면 0개입니다”는 제안이 아니라
막다른 길이므로, 그때는 **어느 조건이 결과를 0으로 만드는지**를 짚어준다.

### 흐름 연결

```
A-13b 전부 불충족
   ├─ (a) → A-15 완화 → 후보 생김 → A-16 정하기
   └─ (b) → 네이버 탐색 → A-20 매물 추가 → 자동 판정 → A-13
                                                  └─ 회차 반복 구조와 같은 경로
```

## ⑤ 확정 후 취소는 별도 기능이 아니다 ✅ 결정

초안에서는 예약 도메인(호텔·항공)의 취소 패턴을 참조해 undo 배너·부분 취소·확인창을
검토했다. **과했다.**

> **호텔·항공 취소는 돈과 자리가 걸려 있어 무겁지만, 우리는 아직 아무것도 예약하지 않았다.**
> 후보 목록을 고친 것뿐이다.

`12-invite-and-input-design` §7의 *“참조를 가져올 때 딸려 오는 것을 찾는다”* 가
여기서도 걸렸다 — 이번에 딸려 온 것은 **예약 도메인의 무거움**이었다.

| 검토했던 것 | 판정 |
|---|---|
| undo 배너 | ✗ 그냥 다시 고르면 된다 |
| 부분 취소 개념 | ✗ 선택 변경일 뿐이다 |
| 확인창 | ✗ 파괴적 행동이 아니다 |
| 취소 사유 묻기 | ✗ 물을 일이 없다 |
| **상대에게 알림** | **✓ 이것만 남는다** |

**A-16i는 독립 화면이 아니라 A-16으로 되돌아가는 것**이고, 상태 하나만 추가된다.
정작 자주 일어나는 것은 취소가 아니라 **매물 소진**(A-16j)이며, 그쪽이 이미 만든
A-16e를 재사용한다.
