# 0. 이 문서에서 먼저 맞출 것

- 역기획 대상은 다방이 아니라 **네이버 부동산**이다.
- Hero Feature는 “공동 적합도 점수”가 아니라 **“조건 충돌 + 양보 지점 설명”**이다.
- AI는 정답 집을 고르는 추천자가 아니라, **두 사람의 차이를 설명하는 조정 보조자**다.
- 계약·대출·등기까지 확장하지 않는다. 이번 프로젝트의 완료는 **방문 후보 합의**다.
- **탐색·지도·매물 DB는 만들지 않는다.** 저장 이후만 담당한다. ← v0.2 추가
- **첫 결과까지 요구하는 입력은 2번**(출근지·예산)**을 넘기지 않는다.** 필수 조건은 그 뒤에 사용자가 원하는 만큼(최대 4개). ← v0.3 개정
- 새 자료가 나오면 이 기준을 강화/수정하는지 먼저 판정하고, 멋있어 보여도 방향이 다르면 보류한다.

### 용어 — 세 갈래로 구분해서 쓴다

| 용어 | 뜻 | 어디에 |
|---|---|---|
| **역기획 대상** | 우리가 뜯어보는 서비스 — 네이버페이 부동산 | 하나뿐 |
| **기준 서비스** | 사용자가 우리 대신 쓸 수 있는 것 = **측정 대상** | §4 Tier 0~3 |
| **참조 서비스** | 우리가 구조를 빌려올 곳 = **설계 대상** | §4 후반 |
| **공유 객체** | A가 후보를 고르는 순간 만들어지는 **별도 공간**(매물 ID + 두 사람의 연결 상태). A의 개인 데이터가 아니라서 **B의 로그인을 뒤로 미룰 수 있는 근거** | `08`·`10` |

> **② 공유 객체는 이 이름 하나만 쓴다.** “공동 공간”·“후보 묶음”으로 부르지 않는다.

# 1. 문제 정의 — “매물을 찾는 문제”가 아니라 “둘이 결정하는 문제”

## AS-IS — 저장부터 시작한다

```
 네이버 안 │  ①저장  ·······································  ⑨찜 목록만 남음
           │    │                                                    ▲
 ──────────┼────┼────────────────────────────────────────────────────┼──────
 네이버 밖 │  ②카톡 공유 → ③각자 열람 → ④통근 확인 → ⑤비용 계산 → ⑥의견 교환 → ⑦메모
           │                                                 │
           │                                                 └─▶ 합의 실패 시 ①로 회귀 ⟲
```

> **핵심 공백** | 네이버 부동산은 탐색과 저장에는 강하지만, **저장 이후 7단계 중 네이버 안에서 일어나는 건 0개**다. 서비스는 ①에서 사용자를 놓치고 ⑧에서 다시 만난다.

**최대 병목은 ⑥이다.** 다른 단계는 *시간이 걸리는* 구간이고, ⑥은 *멈추는* 구간이다.
“그냥 별로”에서 끝나면 ③④⑤에 쓴 노력이 전부 무효가 된다.

## 문제 구조 — 일직선이 아니라 두 갈래

```
[정보의 문제]   Information Fragmentation ──▶ Manual Comparison ─────┐
 혼자 구해도                                                          │
 똑같이 겪음                                                          ├──▶ Decision Cost ──▶ Repeated Search
                                                                      │                            │
[사람의 문제]★  Preference Fragmentation ─▶ Preference Conflict ─────┘                            │
 둘일 때만                                                                                         │
 생김           상대의 기준이 데이터가      "그냥 별로"에서                                        │
                아니라 말로만 존재          대화가 끝남                                            │
      └────────────────────────────────────────────────────────────────────────────────────────────┘
                                    다시 탐색으로 되돌아감
```

> **매물 링크를 한 곳에 전부 모아놔도, 상대는 여전히 “그냥 별로”라고 말한다.**
> 두 문제는 서로 원인이 아니다. 따로 생겨서 Decision Cost에서 처음 만난다.

| | 위 갈래 · 정보 | 아래 갈래 · 사람 ★ |
|---|---|---|
| 누가 겪나 | 혼자 구해도 겪음 | **둘일 때만 생김** |
| 이미 푸는 곳 | 카톡+노션, 1인 임장앱 20개+ (무료) | **없음** |
| 우리 범위 | 아니오 | **예** |

**위 갈래만 고치면 결과물은 공유 폴더다.** 그건 카톡+노션이 이미 하고 있다.

## Problem Statement

> **공동 주거자는 각자의 조건·우선순위·매물 평가를 여러 채널에서 수동으로 비교해야 하며, 특정 매물을 선택할 때 누가 무엇을 양보하는지 명확히 보기 어려워 최종 후보 합의 비용이 커진다.**

“기존 부동산 서비스가 …지원하지 못한다”는 뺐다. 서비스의 결함을 단정하는 문장은 검증 대상이 아니라 주장이다.

## 우리가 답하려는 사용자 질문 — 가운데가 함정이다

```
①  "나에게 좋은 집은 무엇인가?"           ← 기존 부동산 앱
②  "우리 둘에게 가장 좋은 집은?"          ← 함정 ⚠  v0.1이 여기 있었음
③  "우리 둘이 납득할 수 있는 집은?"       ← 우리 ★
```

②로 질문하면 **총점을 안 만들 수가 없다.** “가장”이 순위를 요구하고,
순위는 통근 36분과 면적 7㎡를 같은 자로 재라고 요구한다.

> **납득 = 이 집을 고르면 내가 무엇을 감수하는지 알고, 그걸 알고도 동의한 상태**
> 만족이 아니다. 그래서 `한쪽만 충족`인 매물이 최종 후보가 될 수 있다.

# 2. TO-BE — 공동 의사결정이 끝나는 지점까지

```
관심매물 저장 → 후보 5개 → A 조건 4번 → 초대 → B 조건 4번 → 자동 판정
  → 양보 지점 설명 → 조건 완화 → 방문 후보 2개 → 질문 카드 → 방문 후 유지·보류·제외
```

## 조건 스키마 — 사람 1명당 저장되는 것

```
├─ 출근지      좌표 + 이름 + 이동수단      ← 조건이 아님. 계산 기준점
├─ 예산        월 실부담 상한 1개          ← 상한형
├─ 필수 (0~4)  항목 + 연산자 + 값          ← 판정에 들어감. 개수는 사용자가 정함
├─ 선호 (0~3)  판정 안 함. 표시만
└─ 확인 필요   판정 안 함. 중개사 질문 카드로
```

**처음 요구하는 입력은 2번뿐이다** — 출근지와 예산. 그것만으로 결과가 나온다.
필수 조건은 **사용자가 원하는 만큼, 최대 4개까지** 덧붙인다.

### 개수를 고정하지 않는 이유

초안은 *“필수 슬롯 2개 고정”* 이었다. **근거가 안 버텨서 풀었다.**

| 원래 근거 | 왜 안 버티나 |
|---|---|
| 조건이 많으면 후보 5개가 전멸한다 | **전멸에는 이미 출구가 있다** — 완화 제안 / 재탐색 필터 제안으로 갈라지는 화면(A-13b). 사고가 아니라 처리 경로가 있는 정상 상태다 |
| 입력 부담을 줄여야 초대가 산다 | **점진적 공개가 이미 해결했다.** 중요한 건 처음 요구하는 **최소값**이지 최대값이 아니다. 스스로 4개를 넣는 사람은 이탈 위험이 낮은 사람이다 |
| “둘만 고르세요”가 우선순위를 드러낸다 | **우리는 조건 간 가중치를 안 쓴다.** 우선순위를 받아도 판정에 안 들어가는데 그걸 위해 조건을 자를 이유가 없다 |

무엇보다 **반려동물이 안 되면 절대 못 가는 사람에게 “필수는 둘까지”라고 말하는 게 이상하다.**
세 번째 조건은 `선호`로 밀리는데 선호는 판정에 안 들어간다 — 사용자 입장에선 **필수가 무시된 것**이다.

### 그래도 상한 4를 두는 이유 — 문장이 안 읽힌다

진짜 제약은 후보 수가 아니라 **양보 문장**이다.

```
미충족 1~2개   "A가 역까지 3분 더 걷습니다. 대신 통근은 후보 중 가장 짧고…"   ← 읽힌다
미충족 5개     "A가 3분 더 걷고, 7㎡ 좁고, 주차 없고, 6년 더 됐고, 방이…"      ← 안 읽힌다
```

총점을 안 쓰는 이유 자체가 **대화를 만들려는 것**인데, 목록이 길어지면 총점과 똑같이 대화가 죽는다.
상한 4는 화면 제약이기도 하다 — A·B를 합치면 비교표가 최대 8행 + 예산·통근이고, 그 이상은 한 화면에 안 들어간다.

> **⬜ 남은 미정 — 어떤 항목을 후보로 열어둘지.** 자동 판정이 되는 8개(통근·역 도보·전용면적·방 개수·
> 건물 연식·주차·엘리베이터·층수)가 후보다. 전부 열지 일부만 열지는 안 정했다.
> → `11-decision-status.md` §2

| 타입 | 형태 | 미달 표현 | 해당 항목 |
|---|---|---|---|
| 상한형 | X 이하 | `+3분`, `+월 15만` | 통근, 역 도보, 연식, 예산 |
| 하한형 | X 이상 | `−7㎡`, `−1개` | 전용면적, 방 개수 |
| 유무형 | 있음/없음 | `없음` | 주차 ✓, 엘리베이터 ✓ |

**네 번째 상태 — 확인 필요.** 반려동물은 매물 데이터에 없다.
없는 걸 “안 됨”으로 판정하면 후보가 잘못 탈락하므로 **판정 보류 + 질문 카드**로 처리한다.

## Hero Feature: 조건 충돌 · 양보 지점 분석

| 조건 상태 | 처리 |
| --- | --- |
| 둘 다 충족 | 논의 필요 없음 → 후보 유지 |
| **한쪽만 충족** | **핵심 구간** — 누가 무엇을 감수하고 무엇을 얻는지 설명 |
| 둘 다 불충족 | 후보 제외 또는 조건 자체를 다시 논의 |

> **예시** | “A가 역까지 3분 더 걷습니다(도보 13분). 대신 A의 통근은 34분으로 후보 5개 중 가장 짧고, 실부담은 월 128만원으로 두 번째로 낮습니다.”

### 문장 생성 규칙

```
[누가] [무엇을] [얼마나] 잃고,  [대신] [무엇이] [얼마나] 낫다
```

- **잃는 것** = 미충족 조건 + 미달량 (`A · 역 도보 · +3분`)
- **얻는 것** = **후보 5개 안에서의 조건별 순위** (`통근 최단`, `실부담 2위`)

얻는 것을 절대값으로 말하면 근거가 없다 — “통근 34분”이 좋은 건지 알 수 없다.
**순위는 조건별로만 매기고 조건 간 합산은 금지한다.**

#### 미충족이 3개 이상이면 — 앞 2개만 문장으로

| 미충족 | 출력 |
|---|---|
| 1~2개 | 전부 문장에 넣는다 |
| **3개 이상** | **앞 2개만 문장, 나머지는 그 아래 목록** |

**“앞”은 우리가 고르는 게 아니라 이미 고정된 조건 표시 순서다** —
`예산 → 통근 → 필수① → 필수② → 필수③ → 필수④`.
순위를 새로 매기면 그게 곧 집계이고 `decisions/0001` 위반이다. 그래서 **원래 순서를 그대로 쓴다.**

#### 얻는 것이 없으면 “대신” 절을 지운다

5개 후보 중 아무 조건에서도 1~2위가 아니면 **억지로 만들지 않는다.**
없는 장점을 지어내면 그 순간 우리가 **파는 쪽**이 된다.

```
✗  "대신 실부담이 세 번째로 낮습니다"        ← 5개 중 3위는 장점이 아니다
✓  (대신 절 없이) "B가 통근 7분, 면적 7㎡를 감수합니다."
```

#### A와 B에게 같은 형식을 쓴다

한쪽만 손실을 먼저 쓰거나, 한쪽만 “대신” 절을 붙이면 **그 자체가 편들기**다 (G10 · IPDAS 프레이밍 균형).
문장 개수·순서·길이를 양쪽 동일하게 맞춘다.

## 조건 완화 — 후보 수 증가가 아니라 등급 이동

미달량이 곧 완화폭이므로 **추가 계산이 없다.**

| | 현재 | A가 역 도보 10→13분 | B가 전용 66→59㎡ |
|---|---|---|---|
| 둘 다 충족 | 1개 | **3개 (+2)** | 2개 (+1) |
| 한쪽만 | 3개 | 1개 | 2개 |

**반드시 지킬 것** — ① 양쪽 완화안을 항상 같이 보여준다(한쪽에만 제안하면 “네가 양보해”로 읽힘)
② 완화폭은 미달량에서 그대로 나온다 ③ “이렇게 하세요”가 아니라 “이렇게 하면 이렇게 됩니다”

## 왜 총점을 만들지 않는가

- 공동 적합도 83%처럼 하나의 숫자로 합치면, **어느 사람이 어떤 조건을 양보했는지가 가려진다.**
- 차별점은 “더 높은 점수의 집”이 아니라 **“선택의 trade-off를 대화 가능한 언어로 바꾸는 것”**이다.
- 개인용 매물 채점·가중치·종합점수는 이미 국내 앱에 존재하므로 총점 자체는 차별점이 아니다.
- **표현 주의** — “Least Misery를 안 쓴다”가 아니라 **“집계 자체를 하지 않는다”**가 정확하다. (§4)

## 왜 이 방식인가 — 기각한 대안 넷

| 안 | 어떤 방식 | 왜 안 하나 |
|---|---|---|
| 목록만 공유하고 각자 댓글 | 카톡이랑 똑같음 | **카톡을 두고 이걸 쓸 이유가 없다** |
| **조건을 각각 받아 대조** ★ | **채택** | |
| 상담원이 대신 골라줌 | 사람이 함 | 사람 수만큼 비용이 는다 |
| 주거비 계산기만 | 계산만 | 이미 다섯 군데가 무료로 한다. **계산은 가져다 쓰되 단독 제품으로는 안 만든다** |

계산기 안을 기각한 게 중요하다. 총비용 계산은 바로계산·핀다·EZB가 이미 하고 있고,
우리가 새로 얹는 건 **교통비와 초기비용 둘뿐**이다(`06-cost-model.md` §4).
그 둘도 단독으로는 팔리지 않고, **판정 안의 재료**일 때만 값을 한다.

## AI 역할의 경계

> **AI가 한다** | 조건 구조화 · 충돌 지점 설명 · 조건 완화 시 후보 등급 변화 설명 · 미확인 정보 질문 정리

> **AI가 하지 않는다** | 좋은 집 대신 선택 · 종합점수로 자동 랭킹 · 대출 가능액/금리 확정 단정 · 한쪽에만 완화 제안

### v0.1의 “충돌 표현 참조 없음”이 해소됐다

> v0.1: **국내 부동산에는 참조할 것이 없습니다.** 타 도메인에서 가져와야 합니다.

**의료 분야에 20년 넘게 표준화된 참조군이 있었습니다.**
환자 의사결정보조자료(PtDA)의 국제 표준 **IPDAS**와 그 화면 형식 **Option Grid**입니다.

IPDAS의 balanced information 정의:

> …어떤 옵션도 다른 옵션보다 선호하지 않는 방식으로 제시하고
> (*in a way that does not favor one option over another*),
> 개인이 중요한 요소에 주의를 집중해 정보를 처리할 수 있게 한다.
> — Martin et al., *Medical Decision Making*, 2021

| IPDAS 권고 | 우리 적용 | 상태 |
|---|---|---|
| **Side-by-side 제시** (40개 연구 중 28개, 균형 인식률 70~96%) | A/B 좌우 배치 | ✅ 이미 적용 |
| **개인 가치 우선 순서** — 중요 속성을 먼저 제시하면 가치일치 선택 **70% → 90%** | 조건 표시를 **필수 → 선호 → 확인** 순으로 고정 | ⚠️ **규칙으로 못박을 것** |
| 모든 합리적 옵션 제시 (아무것도 안 하는 선택 포함) | `둘 다 불충족`도 숨기지 않음 + “더 찾아보기” 경로 | ⚠️ 경로 검토 |
| 손실/이득 프레임 균형 | 양보 문장의 **손실·이득 순서를 A·B 동일하게** | ⚠️ **FT5 명세 보강** |
| 평가적 조건화 금지 (사진·증언이 편향을 만듦) | 매물 사진을 판정 화면에서 강조하지 않음 | ⚠️ 14번 검토 |
| 주의 조작 금지 (강조 차등) | **A와 B 블록의 시각 비중 동일** | ⚠️ **명시할 것** |

**Option Grid와 우리의 축이 다르다.**

```
Option Grid   열 = 선택지 (수술 / 물리치료 / 경과관찰)   ← 한 사람이 여러 옵션을 비교
우리          열 = 사람 (A / B)                          ← 두 사람이 한 옵션을 본다
```

형식은 빌려오되 행에 무엇을 둘지는 우리가 정한다 — **우리 행은 “조건”이다.**
정보량 실증(1,565 vs 846단어가 지식 변화에 유의미한 차이 없음)은 그대로 적용된다 —
**길게 쓴다고 더 이해되지 않는다.**

### 우리가 안 쓰는 집계 전략의 정확한 이름

| 전략 | 계산 | 판단 |
|---|---|---|
| Additive Utilitarian | 개인 점수의 **합** | ✗ 총점 |
| **Least Misery** | 개인 점수의 **최솟값** | △ **부분 채택** ↓ |
| Most Pleasure | 최댓값 | ✗ 한쪽 무시 |
| Majority / Approval Voting | 투표 | ✗ 2인에서 무의미 (1:1 동점) |

```
Least Misery   min(A,B) 만 남기고 나머지 탈락 → "한쪽만 충족"은 그냥 떨어진다
우리           min(A,B) 로 등급을 나누되 <한쪽만 충족>을
               탈락이 아니라 <설명 대상>으로 승격 → 왜 낮은지를 문장으로 되돌려준다
```

**발표 표현** — “Least Misery를 쓰지 않습니다”가 아니라
**“집계 자체를 하지 않고 차이를 그대로 보여줍니다”**가 정확하다.

| 기존 경쟁 강도 | 높음 | “매물 더 잘 찾기”로 경쟁하지 말고 **저장 이후 공백**을 공략 |

| 대체재 위협 | 매우 높음 | 카톡·지도·엑셀·메모장이 이미 workflow를 구성 |
| 신규 진입자 위협 | 중간 | 매물 데이터·트래픽·브랜드 신뢰가 장벽 → **네이버 자산 활용이 유리** |
| 공급자 교섭력 | 중~높음 | 새 DB 구축이 아니라 **기존 매물 위에 의사결정 레이어** |

```

```

## KSF

- 매물 데이터의 풍부함·신선도 / 지도·필터 탐색 속도 *(네이버가 이미 가진 것)*
- **관심매물 저장 이후 다시 돌아오게 하는 후보 관리**
- **2인 참여를 깨지 않는 초대·입력 마찰 최소화**

## MVP에 반드시 들어가는 예외 다섯

| 상황 | 처리 |
|---|---|
| **B가 초대에 안 들어옴** | **1인 빈 경로** — A는 자기 조건 판정·실부담·통근을 혼자 봄. 교통비 1인분 표시 |

# 7. 성공 지표 — 찜이 늘어나는 건 성과가 아니다

오히려 **오래된 찜이 쌓이는 게 지금의 문제**다. 그래서 저장 수를 지표로 쓰지 않는다.

## North Star — 하나만 고르면 이것

> **초대를 보낸 것 중에서, 7일 안에 「보러 갈 집 2개」까지 정해진 비율**

중간 단계가 아니라 **종료점**을 재는 이유는, 초대 수락률만 좋고 아무것도 안 정해지는 상태를
성공으로 착각하지 않기 위해서다. (7일이 맞는 기간인지는 1차 측정 후 조정한다.)

## 선행 지표 — 먼저 움직이는 것

| 뭘 보나 | 목표 |
|---|---|
| **초대 수락률** — 보낸 것 중 상대가 조건까지 넣은 비율 | `측정 필요` · **최우선** |
| 양쪽이 조건을 다 넣었나 | `측정 필요` |
| 보러 갈 2곳을 정했나 | `측정 필요` |

## 후행 지표 — 나중에 따라오는 것

| 뭘 보나 | 방향 |
|---|---|
| 중개사에게 연락한 비율 | 오르면 좋음 |
| 다녀와서 '제외'로 끝난 비율 — **헛걸음 지표** | 내려가면 좋음 |
| 한 달 넘게 방치된 찜 비율 | 내려가면 좋음 |
| 전월세대출 비교로 넘어간 비율 | 오르면 좋음 |

**숫자가 비어 있는 건 기준값이 없어서다. 지어내지 않았다** (G6).

# 8. 리스크 — 무엇이 잘못될 수 있나

| 위험 | 영향 | 미리 알 수 있는 신호 | 어떻게 |
|---|---|---|---|
| **상대가 안 들어온다** | **치명적** | 초대 수락률이 2주 만에 바닥 | 조건 없이 O/X만 찍는 형태로 줄여서 재측정 → `decisions/0002` |
| 계산한 비용이 실제와 다르다 | 큼 | “이 숫자 뭐예요” 반응 | 숫자 옆에 전제를 항상 붙인다. 단정하지 않는다 (G3) |
| 매물이 너무 빨리 사라진다 | 중간 | 후보 중 거래완료 급증 | 조건을 사람에 저장해 다음 매물에 재사용 → `decisions/0003` |
| **충돌 화면이 싸움을 키운다** | 중간 | 그 화면 이후 이탈 증가 | 이기고 지는 표현을 안 쓴다. 주고받는 문장으로만 (G10) |
| 상대에게 예산·직장이 노출된다 | 중간 | 조건 입력하다 나감 | 항목별 공개 범위 선택. 충족 여부만 보이고 숫자는 숨기는 옵션 |

**네 번째가 과소평가되기 쉽다.** 우리가 만드는 화면은 *“누가 무엇을 포기하는지”* 를 보여주는데,
그건 **잘못 쓰면 싸움의 근거가 된다.** IPDAS의 균형 제시 규칙(G10)이 그래서 장식이 아니다.

# 9. 바로 팀에 던질 결론

> **우리가 만드는 것은 “AI가 좋은 집을 추천하는 기능”이 아니다.
> 네이버 부동산의 관심매물 이후 단계에서, 두 사람이 각자 중요하게 보는 조건과 그 충돌을 한 화면에 모으고,
> 선택할 때 발생하는 양보 지점을 설명해 ‘이번에 보러 갈 집 2개’를 합의하도록 돕는 기능이다.**

- **차별점** — 공동 적합도 점수보다 trade-off 설명. **집계를 하지 않는다**는 것 자체가 설계 판단
- **수요 검증의 급소** — 상대가 실제로 들어오는가(**H1**), 둘이라서 결정 비용이 커지는가(**H2-b-2**)
- **경쟁 기준선** — 다른 부동산 앱보다 **카카오톡 + 지도 + 메모**
- **산업상 위치** — 매물 데이터를 새로 만들지 않고 네이버 자산 위에 **공동 결정 레이어**를 추가
- **설계 근거** — 총점 미사용과 균형 제시는 **의료 PtDA의 IPDAS 표준**이 지지한다 (v0.2 신규)

## 진행 순서 — 검증이 제작보다 먼저다

v0.1은 `MVP·프로토타입 제작 → KPI 및 검증 설계` 순이었다. **순서가 반대다.**

```
✅ 완료   문제 가설 · AS-IS · 경쟁/참조 분석 · Solution 정의 · MVP/화면 · KPI 설계
⏳ 진행   타깃 사용자 인터뷰(H2-b-2) · 참조 서비스 실사용(위밋플레이스 → 웨딩노트/특별시 → 집노트)
⬜ 다음   H1 선행 측정 → 프로토타입(단계 1) → H3 → H4·H5 병행
```

**H1 선행 측정은 조건 대조 로직 없이** 목록 공유 + O/X 반응만 있는 최소 형태로 한다.
조건 대조와 비용 환산을 다 만든 뒤 초대가 안 된다는 걸 알면 그때까지의 작업이 전부 매몰된다.
