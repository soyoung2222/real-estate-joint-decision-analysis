# 같이 고르는 집 — 기능 제안

네이버페이 부동산 내 기능으로 상정한 역기획입니다.
네이버와 무관한 개인 작업이며, 공식 로드맵이나 실제 논의와는 관계가 없습니다.

**상태: 가설 검증 전.** 렌더링된 버전: `assets/proposal.html`

---

## 한 문장 정의

> 함께 집을 구하는 두 사람이 최대 5개 관심매물의 필수조건·통근·실질 주거비·미확인 정보를
> 비교하고, 방문 후보 2개를 정한다.

핵심은 **어느 집이 더 좋은지 점수를 매기는 것이 아닙니다.**
A를 고르면 누가 무엇을 양보하게 되는지를 눈에 보이게 만드는 것입니다.

## 01. 기획 해석

| 항목 | 내용 |
|---|---|
| **문제** | 관심매물이 5개를 넘어가면 무엇이 무엇이었는지 구분되지 않고, 상대의 조건은 한 번도 명시된 적이 없어 "그냥 별로야"로 대화가 끝난다. 비교는 매번 처음부터 다시 시작된다 |
| **사용자** | 함께 살 집을 정해야 하는 2인. 주 사용자는 검색을 도맡는 **주도자**이지만, 가치는 **상대**가 들어와야 발생한다 |
| **목표** | 더 많은 매물을 보게 만드는 것이 아니라, **이번 주에 볼 2개를 자신 있게 고르게** 만드는 것. 헛방문을 줄이는 쪽이 성과 |
| **제약** | 네이버 보유 데이터는 보증금·월세·관리비·위치까지. 실제 대출 조건, 관리비 세부내역, 교통비는 없음. 매물은 며칠 만에 사라짐 |
| **성공 기준** | 초대받은 상대가 실제로 들어와 조건을 입력하고, 두 사람이 방문 후보 2개에 합의하며, 방문 뒤 '제외'로 끝나는 비율이 줄어드는 것 |

**재해석 고지** — 원 요청은 "찜에서 방문·계약 전 확인까지 연결"이었습니다.
위 문제 정의는 그 요청이 함의하는 문제를 재구성한 것이며, 재구성의 책임은 이 문서에 있습니다.

## 02. 왜 지금인가

사용자가 관심매물을 저장한 뒤에 하는 일은 대부분 서비스 밖에서 벌어집니다.

```
[현재]                              [제안]
관심매물 저장                        공동 후보군 (최대 5)
  ├→ 카카오톡 공유                     ↓
  ├→ 지도에서 통근 확인                조건 충돌 확인
  ├→ 대출 계산기                       ↓
  ├→ 중개사 문의                       미확인 정보 질문 생성
  ├→ 방문 일정 조율                    ↓
  └→ 메모장에 장단점                   방문 순서 결정
                                       ↓
  돌아오는 경로 없음                   현장 확인 기록
  남는 것: 오래된 관심매물 목록          ↓
                                     유지 · 보류 · 제외
                                       ↓
                                     (제외하면 자리가 비고 다음 매물이 들어옴)

                                     밖으로 나가는 것은 둘뿐:
                                     중개 문의 · 전월세대출 비교 (네이버페이 금융)
```

**새 행동을 요구하는 제안이 아니라, 흩어져 있는 같은 행동을 한 자리에 잇는 제안입니다.**
그래서 경쟁 상대는 다른 부동산 앱이 아니라 카카오톡·엑셀·메모장·지도·대출 계산기입니다.

조사 결과 요약은 `02-research-2026-08.md`, 비교 대상 정리는 `04-benchmarks.md`.

## 03. 대안 비교

옵션은 기능의 크기가 아니라 **누가 일하고 무엇이 자동화되는지**로 나눴습니다.

| 안 | 구조 | 사용자 가치 | 실행 비용 | 기술 위험 | 운영 부담 | 검증 가능성 |
|---|---|---|---|---|---|---|
| A · 공유 폴더 | 목록을 둘이 공유하고 각자 코멘트 | 낮음 | 소 | 낮음 | 낮음 | 높음 |
| **B · 조건 대조** ★ | 각자 필수조건·출근지를 걸고 매물별 충족·충돌 자동 대조 | **높음** | 중 | 중 | 낮음 | **높음** |
| C · 상담 중개 | 두 사람 조건을 받아 상담원·중개사가 후보를 추림 | 높음 | 중 | 낮음 | **높음** | 낮음 |
| D · 비용 계산기 | 실질 주거비만 환산하는 단독 도구 | 중 | 소 | 낮음 | 낮음 | 높음 |

### 추천 근거

**B를 선택합니다.** 결정적인 축은 사용자 가치와 검증 가능성이었습니다.

| 기각 | 이유 |
|---|---|
| **A** | 경쟁 상대가 카카오톡인데 카카오톡이 하는 일을 그대로 옮겨오면 옮겨올 이유가 없다 |
| **C** | 운영 인력이 사용자 수에 비례해 늘고, 이미 오프라인 동행 서비스가 하는 영역 |
| **D → 흡수** | 단독으로는 리텐션이 없고 총비용 계산기는 이미 다섯 곳 이상이 무료 제공. **다만 실질 주거비 환산은 B의 필수 구성요소로 그대로 가져간다** — 양보를 금액으로 환산할 재료가 이것뿐 |

D를 흡수하되 **계산에 쓴 전제를 공개**합니다. → `03-cost-model.md`

> 대출금리 4.2%를 적용한 추정치이며, 실제 금리는 심사 결과에 따라 달라질 수 있습니다.
> 보증금 기회비용은 연 3.0% 예금금리 기준입니다.

전제 공개는 정직함의 문제만이 아닙니다. 금리·한도를 단정해 제시하면
유사 금융자문 소지가 생깁니다. 전제를 드러내는 설계가 그 방어선과 같은 자리에 있습니다.

## 04. 작동 방식 — 총점이 아니라 충돌

```
나의 조건   ─┐
             ├─→  매물 카드 (최대 5)  ─┬─→  둘 다 충족    → 후보 유지
상대의 조건 ─┘      항목별 대조         ├─→  한쪽만 충족  → 양보 지점 ★
                                        └─→  둘 다 불충족 → 후보 제외
```

가운데 갈래 하나가 이 제품이 존재하는 이유입니다. 출력은 점수가 아니라 문장입니다.

> "A를 고르면 통근 왕복 36분과 교통비 월 4만원을 상대가 부담하고,
> 실질 주거비는 월 12만원 싸다."

근거: `decisions/0001-no-total-score.md`

## 05. 사용자 플로우

| # | 단계 | 내용 |
|---|---|---|
| 1 | 진입 | 관심매물 3개째 저장 시점에 "같이 볼 사람이 있나요?" 한 줄. 처음부터 묻지 않는다 |
| 2 | 초대 | 링크 하나. 상대는 가입 없이 열어보고, 조건 입력할 때만 로그인. **여기가 생사 지점** |
| 3 | 조건 입력 | 필수조건 3개까지, 출근지 1곳, 예산 상한. 한 번에 다 묻지 않는다 |
| 4 | 공동 후보군 | 최대 5개. 6개째를 넣으려면 하나를 빼야 한다. **제한이 곧 기능** |
| 5 | 조건 충돌 확인 | 매물별 양보 지점. 실질 주거비 차액과 통근 차이가 같은 화면에 |
| 6 | 질문 생성 | 관리비 포함 항목, 전입신고·대출 가능 여부 등 매물 정보에 없는 것을 질문 카드로 |
| 7 | 방문 순서 결정 | 후보 2개와 순서. **여기까지가 목표 지점** |
| 8 | 현장 기록 → 상태 전이 | 유지·보류·제외. 제외하면 자리가 비고 다음 매물이 들어온다 |

### 빈 경로와 실패 경로

| 상황 | 처리 |
|---|---|
| 상대가 아직 안 들어옴 | 혼자서도 실질 주거비와 통근은 보인다. **초대는 권유이지 관문이 아니다** |
| 매물이 사라짐 | '거래완료'로 표시하고 비교 근거는 남긴다. **조건은 매물보다 오래 산다** |
| 조건이 하나도 안 겹침 | 후보를 추천하는 대신 "예산과 지역 중 무엇을 먼저 조정할지"를 묻는다 |

## 06. 성공 지표

관심매물 저장이 늘어나는 것은 성과가 아닙니다.
오히려 오래된 관심매물이 쌓이는 것이 지금의 문제입니다.

| 구분 | 지표 | 목표 | 측정 창 |
|---|---|---|---|
| 선행 | **초대 수락률** — 발송 대비 상대가 조건까지 입력한 비율 | `측정 필요` · 최우선 | 2주 |
| 선행 | 양쪽 조건 입력 완료율 | `측정 필요` | 2주 |
| 선행 | 방문 후보 2개 확정률 | `측정 필요` | 4주 |
| 후행 | 조건이 맞는 매물의 중개 문의 전환 | 기존 대비 상승 | 8주 |
| 후행 | 방문 후 '제외' 비율 — 헛방문 대리 지표 | 기존 대비 하락 | 8주 |
| 후행 | 30일 이상 방치된 관심매물 비중 | 기존 대비 하락 | 12주 |
| 후행 | 전월세대출 비교 진입 | 기존 대비 상승 | 12주 |

## 08. 다음 실행 티켓

순서를 뒤집으면 안 됩니다. **1번이 실패하면 2번 이후는 만들 이유가 없습니다.**

**1. 초대 수락률 측정 — 조건 대조 없이**
- 범위: 관심매물 목록 공유 링크 + 상대가 각 매물에 O/X만 남기는 최소 화면
- 완료 기준: 초대 발송·열람·수락·최초 반응이 각각 계측되고 2주치 코호트 값이 나온다

**2. 조건 모델 정의**
- 범위: 필수조건 후보 항목 확정, 출근지·예산 입력 위치 결정, 조건의 저장 주체를 사용자로 귀속
- 완료 기준: 매물이 사라져도 조건이 살아남는 것을 데이터 모델로 확인

**3. 실질 주거비 환산기 — 전제 공개 포함**
- 범위: 6개 비용 항목 환산식, 각 항목의 전제와 출처 문구, 기본값 근거 명시
- 완료 기준: 모든 숫자 옆에 전제가 붙고, 단정 표현이 하나도 남지 않는다

**4. 충돌 뷰**
- 범위: 두 조건의 매물별 대조, 세 갈래 분기, 양보 문장 생성
- 완료 기준: 종합점수 UI가 어디에도 없고, 출력이 항상 문장 형태다

**5. 미확인 정보 질문 카드 · 방문 후보 확정**
- 범위: 매물 정보에 없는 항목을 질문으로 변환, 후보 2개 확정과 상태 전이
- 완료 기준: 제외 시 후보 자리가 비고 다음 매물이 들어오는 순환이 동작
