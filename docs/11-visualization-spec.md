# 시각화 명세 — 무엇을 어디에 어떻게 보여줄 것인가

*2026-08-19*
**형태를 먼저 정하고 색은 마지막에 정한다.** 대부분의 나쁜 차트는 색부터 고른다.

---

# 1. 원칙 — 시각화가 몰래 총점을 만들 수 있다

가장 큰 위험은 화면에 `%`가 없어도 **면적·길이·거리가 종합 점수로 읽히는 것**이다.
`decisions/0001`은 숫자만 금지한 게 아니라 **합산 자체**를 금지한다.

| 형태 | 왜 위험한가 | 판정 |
|---|---|---|
| **레이더 / 스파이더 차트** | 조건 5개를 축으로 그리면 **면적이 곧 총점**이다. 그리고 축 순서만 바꿔도 면적이 달라진다 | **금지** |
| **A·B를 겹친 레이더** | 누가 더 만족하는지가 면적 비교로 읽힘 → 편들기 (G10) | **금지** |
| **종합 게이지 · 도넛** | 하나의 값으로 뭉침 | **금지** |
| **후보 순위 리스트** | 정렬 자체가 랭킹 | **금지** |
| **별점 · 하트 개수** | 척도가 곧 점수 | **금지** |
| **누적 막대로 조건을 쌓기** | 총 길이 = 합산 | **금지** |
| **이중 축** (통근 시간 + 비용을 한 차트에) | 두 척도를 겹치면 아무 관계나 만들어 보임 | **금지** |

> **판정 규칙** — 조건 여러 개가 **하나의 도형·길이·면적으로 합쳐지면 위반.**
> 조건은 언제나 **각각 따로** 표현하고, 옆에 나란히 둘 뿐 더하지 않는다.

# 2. 색 규칙 — 두 체계가 충돌하고 있다

지금 설계에는 색이 하는 일이 둘이고, 서로 싸운다.

```
identity   A / B 를 구분          → 사람
status     충족 / 미충족 / 확인   → 판정
```

**한 화면에 둘 다 색으로 쓰면 무엇이 무엇인지 알 수 없다.**
A가 초록이고 충족도 초록이면, 초록 점이 "A"인지 "충족"인지 매번 헷갈린다.

## 결정

| | 무엇으로 구분하나 |
|---|---|
| **A / B (identity)** | **위치 + 라벨.** 색을 쓰지 않는다 |
| **충족 / 미충족 / 확인 필요 (status)** | **색 + 아이콘 + 라벨.** 색은 여기에만 |

두 가지 이유다.

**① status가 이 화면의 핵심 정보다.** 사용자가 알고 싶은 건 "A의 것"이 아니라 "되는가 안 되는가"다.
**② A/B에 다른 색을 주면 그 자체가 차등이 될 수 있다.** IPDAS의 *주의 조작 금지* — 강조 차등이 편향을 만든다(G10).
   좌우 배치와 동일한 크기·같은 서체가 균형을 보장한다.

> **주의** — 발표 문서(`assets/reverse-planning.html`)에서는 A=틸, B=플럼으로 색을 줬다.
> 그건 **읽는 문서**라 identity가 핵심이기 때문이고, **제품 화면은 반대**다.
> 문서의 색 선택을 제품에 그대로 옮기지 않는다.

## status 색은 예약한다

| 상태 | 역할 | 아이콘 필수 |
|---|---|---|
| 충족 | good | ✓ |
| **미충족** | **warning** — critical이 아니다 | ✗ |
| 확인 필요 | neutral/info — **경고가 아니다** | ? |
| 둘 다 불충족 | muted (후보에서 내려감) | — |

**미충족을 빨강(critical)으로 쓰지 않는다.** 조건을 못 채운 건 오류가 아니라 협상 지점이다.
빨강을 쓰면 "이 집은 틀렸다"로 읽혀 `한쪽만 충족`을 후보로 유지하려는 설계와 싸운다.

**확인 필요를 경고색으로 쓰지 않는다.** 모른다는 것이지 나쁘다는 게 아니다.

색은 **절대 단독으로 상태를 전달하지 않는다** — 항상 아이콘 + 라벨과 함께.

# 3. 화면별 — 사용자의 질문에서 형태를 고른다

## ② 내 조건 입력

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| 지금 몇 번째지, 얼마나 남았지 | 2단계 진행 표시 | **스텝 인디케이터** |
| **40분이면 대체 어디까지지?** | **내 후보 5개의 실제 시간을 바로 보여줌** | — (차트가 아니다) |
| 66㎡가 감이 안 온다 | 기존 거주지·아는 평형과 비교 | **레퍼런스 마커** |

## 아이소크론을 폐기한 이유

초안에서는 출근지 기준 도달 범위를 지도에 칠하는 **아이소크론(isochrone·등시선)**을
이 화면의 핵심으로 뒀다. **모바일 검토에서 폐기했다.**

| 문제 | 내용 |
|---|---|
| 형태가 안 읽힌다 | 등시선은 대중교통 노선을 따라 **삐죽삐죽 뻗은 불규칙한 형태**다. 작은 화면에서 윤곽 자체가 판독되지 않는다 |
| 겹치면 더 어렵다 | 두 개를 겹치면 색이 섞여 어디가 교집합인지 구분이 안 된다 |
| 조작 부담 | 확대·축소가 필요한데, **입력 단계에서 그건 마찰**이다 |
| **강조 차등** | 입력 화면에서 지도를 크게 쓰면 **위치가 다른 조건보다 중요해 보인다** — G10 |

그리고 더 근본적인 이유가 있다. **아이소크론은 위밋플레이스의 필요이지 우리 필요가 아니었다.**

```
위밋:  후보를 찾아야 한다     →  공간 전체를 봐야 한다  →  지도가 필수
우리:  후보가 이미 5개 있다   →  그 5개만 보면 된다     →  지도가 왜 필요한가
```

“40분이 어느 정도인지”를 **추상적 범위로 보여줄 이유가 없다.** 내 후보의 실제 시간으로 답한다.

```
✗  지도에 40분 영역 칠하기
✓  상도동 28분 · 흑석동 34분 · 신길동 52분
```

점진적 공개로 **입력 직후 바로 결과가 나오므로**(`12-invite-and-input-design`),
그 결과가 곧 범위 설명이다. 별도 시각화가 필요 없다.

### 조건 모순(A-13c)도 지도 없이 설명된다

```
두 분 조건을 동시에 만족하는 후보가 없습니다.

  A · 강남역 20분 이내      가장 가까운 후보: 상도동 28분  (+8분)
  B · 여의도역 20분 이내    가장 가까운 후보: 신길동 14분  ✓

  같은 집이 두 조건을 다 만족하지는 못합니다.
```

**“서울에 그런 곳이 없다”고 주장하지 않는다** — 근거가 없다.
우리가 말할 수 있는 건 **“이 5개 중에는 없다”** 뿐이고 그게 정확한 진술이다.

지도는 **출근지를 고를 때 검색 결과를 확인하는 용도**로만 쓴다.

## ④ 후보 목록

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| 5개 중 뭐가 살아있나 | 3분류 그룹 헤더 + 개수 | **그룹 카운트** |
| 이건 왜 여기 있지 | 카드에 미달 요약 한 줄 | **인라인 배지** |
| 어느 게 아깝나 | **미달량이 작은 순으로 정렬** | — |

`한쪽만 충족` 그룹 안에서는 **미달량이 작은 것을 위에 둔다.** 종합 순위가 아니라
"조금만 양보하면 되는 것"을 앞에 두는 것이라 총점이 아니다. 정렬 기준을 화면에 밝힌다.

## ⑤ 매물 상세 판정 ★

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| **얼마나 모자란 거지?** | **임계값 마커 + 실제값 바** | **불릿 차트(bullet chart)** ★ |
| 나랑 상대가 뭐가 다른 거지 | 두 값을 선으로 잇기 | **덤벨 차트(dumbbell)** |
| 이 집이 뭐가 나은데 | 5개 후보 중 위치를 점으로 | **점 플롯(dot plot) · 스트립 플롯** |

**불릿 차트가 이 화면의 답이다.** Stephen Few가 게이지를 대체하려고 만든 형태로,
**목표(임계값)와 실제값을 한 줄에** 놓는다. 우리 조건 판정과 구조가 정확히 같다.

```
역 도보   ├────────────┼──▓──┤        13분   ✗  +3분
          0           10분  13
                       ▲ 내 기준

통근      ├──────▓─────┼──────┤        34분   ✓
          0          34   40분
                          ▲ 내 기준
```

게이지가 아니라 불릿을 쓰는 이유는 셋이다.
① **한 줄에 여러 개를 쌓을 수 있다** — 조건 3개를 세로로 나열해도 읽힌다
② **미달량이 길이로 바로 보인다** — `+3분`을 숫자로도 길이로도
③ **게이지는 원형이라 면적으로 읽혀 총점 인상을 준다**

"이 집이 뭐가 나은데"에는 **점 플롯**이 답한다. 5개 후보의 통근 시간을 한 줄에 점으로 찍고
이 매물만 강조하면, **총점 없이도 상대 위치**가 보인다.

```
통근시간   ●    ●  ◉      ●        ●
          22   28  34    45       52     ← ◉ 가 이 매물. 5개 중 3번째
```

## ⑥ 조건 완화 ★★

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| **얼마나 풀면 뭐가 달라지지?** | 핸들을 끌면 결과가 실시간 변화 | **제약 완화 미리보기 (constraint relaxation preview)** ★ |
| 등급이 어떻게 옮겨가지 | 완화 전/후를 선으로 연결 | **슬로프 그래프(slope graph)** |
| 어느 조건을 푸는 게 이득이지 | 조건별 효과를 나란히 | **다이버징 바** 또는 **정렬된 바** |

**이 화면이 가장 중요하고 가장 어렵다.** 핵심은 **드래그하는 동안 결과가 따라 움직이는 것**이다.

```
A · 역 도보     10분 ────●──── 13분        [드래그 중]
                             ↑
                        여기까지 풀면

  둘 다 충족   1 ━━━━━━▶ 3        (+2)
  한쪽만       3 ━━━━━━▶ 1
  둘 다 불충족 1 ━━━━━━▶ 1
     ↑ 슬로프 그래프 — 두 상태를 선으로 연결
```

**양쪽 완화안을 항상 같이 보여준다(G1).** 슬라이더도 A용·B용 둘을 동시에 놓는다.
하나만 있으면 그 사람이 양보하라는 뜻이 된다.

## ⑦ 방문 후보 확정

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| 최종 2개를 어떻게 비교하지 | 행=조건, 열=매물, 점수 없음 | **비교 표 (Option Grid 형식)** |
| 실부담 차이가 어디서 나지 | 항목별 증감을 누적으로 | **워터폴 차트** |

```
                 후보 A      후보 B
 A 통근          34분 ✓      52분 ✗ +12분
 A 역도보        13분 ✗ +3분  7분 ✓
 B 전용          68㎡ ✓      59㎡ ✗ −7㎡
 B 주차          있음 ✓      있음 ✓
 실부담          128만       121만
 반려동물        ? 확인      ? 확인
```

**총점 행이 없다.** 이게 Option Grid를 그대로 따르는 지점이다.

**워터폴**은 "왜 이 집이 7만원 싼가"에 답한다.

```
후보A 128만 ┃
  월세        −5만  ▼
  관리비      +2만  ▲
  교통비      −4만  ▼   ← B의 통근이 짧아져서
후보B 121만 ┃
```

## ⑧ 방문 후 기록

| 사용자의 질문 | 형태 |
|---|---|
| 뭘 확인해야 하지 | 체크리스트 |
| 둘 다 봤나 | **완료 상태 2개를 나란히** — 진행률 아님 |

# 4. 시각화 용어 사전

찾던 용어가 여기 있을 것이다.

| 용어 | 무엇 | 우리에게 |
|---|---|---|
| **불릿 차트** bullet chart | 임계값 마커 + 실제값 바. 게이지 대체용 | **★ ⑤의 핵심** |
| **게이지** gauge | 반원 눈금 + 바늘 | ✗ 원형이라 총점으로 읽힘 |
| **덤벨/DNA 차트** dumbbell | 두 값을 선으로 연결 | **○ A·B 차이 표현** |
| **슬로프 그래프** slope graph | 두 상태(전/후)를 선으로 | **★ ⑥ 완화 전후** |
| **점 플롯 / 스트립 플롯** dot/strip plot | 값들을 한 축에 점으로 | **★ 5개 중 상대 위치** |
| **다이버징 바** diverging bar | 기준선 좌우로 뻗음 | ○ 초과/미달 |
| **범위 바** range bar | 최소~최대 구간 | ○ 예산 범위 |
| **워터폴** waterfall | 항목별 증감 누적 | **○ ⑦ 비용 차이** |
| **아이소크론** isochrone | 시간 거리 등고선 | **✗ 폐기** — 모바일 판독 불가 + 위치를 과대 강조 |
| **아이콘 배열** icon array | 100개 아이콘 중 N개 색칠. 의료 위험 전달 표준 | △ 확률을 다루면 |
| **스텝 인디케이터** step indicator | 다단계 진행 표시 | ○ ② 4단계 |
| **레이더/스파이더** radar | 다축 방사형 | **✗ 면적=총점** |
| **평행 좌표** parallel coordinates | 여러 축을 세로로 나열, 선으로 연결 | △ 조건 많을 때. 2인엔 과함 |
| **파레토 프론티어** Pareto frontier | trade-off 곡선의 최적 경계 | △ 개념은 맞으나 5개엔 과함 |
| **히트맵** heatmap | 격자 × 색 농도 | △ 매물×조건 격자로 가능 |
| **스파크라인** sparkline | 축 없는 초소형 추세선 | ✗ 시계열이 없음 |

# 5. 참조 서비스 — 직접 볼 것

**각 항목에 "무엇을 볼지"가 붙어야 탐색이 감상으로 끝나지 않는다.**

## A. 제약 완화 미리보기 — ⑥의 직접 참조 ★★

우리 F6과 **구조가 같은** 기능을 이미 하는 곳들이다. 여기가 가장 중요하다.

| 서비스 | 어디를 볼까 | 무엇을 볼까 |
|---|---|---|
| **스카이스캐너** | 항공권 검색 → **“가장 저렴한 날짜”·±3일 달력** | **조건(날짜)을 풀면 결과가 어떻게 변하는지 보여주는 방식.** 우리 완화와 논리가 동일 |
| **아고다 / 부킹닷컴** | 숙소 필터 사이드바 | **필터 옆의 “(+34)” 표기** — 이 필터를 풀면 몇 개가 늘어나는지 미리 보여줌 |
| **에어비앤비** | 필터 → 결과 0건일 때 | **막다른 길 처리** — “필터를 지우면 N개” 안내. 우리 `전부 불충족` 화면의 직접 참조 |
| **호갱노노** | 지도 필터 조작 | **드래그하는 동안 지도가 실시간으로 반응하는 속도감.** 국내 부동산 최고 사례 |
| **네이버 항공권** | 최저가 달력 | 완화 결과를 달력 격자로 보여주는 방식 |

> **핵심 관찰 포인트** — 이들은 전부 **“조건을 풀면 +N개”**를 보여준다.
> 우리는 개수가 아니라 **등급 이동**을 보여줘야 한다(후보가 5개뿐이라).
> 같은 논리를 다른 출력으로 옮기는 게 설계 과제다.
