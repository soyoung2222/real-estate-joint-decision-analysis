# 화면 인벤토리 — 빠짐없이 나열하기

*2026-08-19 · 2026-08-20 개정(집계 재계산 · 프로토타입 반영)*
**와이어프레임 전 단계.** 무엇을 그려야 하는지 목록을 먼저 확정한다.
정상 경로만 세면 8개지만, 빈 상태·예외·전이를 포함하면 **100개**다.
**그중 실제로 그릴 와이어프레임은 핵심 8장이다** — 목록과 그림의 분량은 다르다.

## 기기 전제 — A는 PC 웹, B는 링크 ✅ 결정

초안은 모바일 뷰를 전제로 그렸다. **접근 경로를 보면 그렇지 않다.**

| 경로 | 마찰 |
|---|---|
| 네이버페이 **앱** | 부동산이 **하단 네비바에 작게** 들어 있어 진입 자체가 눈에 안 띈다 |
| **웹** | 검색해서 들어가야 하지만, **일단 들어오면 화면이 넓다** |

```
A (초대자)   PC 웹 우선     후보 고르기·조건 입력·판정 확인은 정보 밀도가 높다
B (수신자)   기기 무관      카톡 링크로 들어오므로 모바일일 확률이 높다
```

**A와 B의 기기가 다를 가능성이 높다.** 따라서 화면을 둘로 나눠 설계한다.

| 화면 | 기준 |
|---|---|
| A-02 후보 선택 · A-13 후보 목록 · A-14 상세 판정 · A-15 완화 | **PC 웹 우선** — 좌우 비교와 슬라이더+결과 동시 표시가 필요 |
| B-01~B-05 초대 진입 · 조건 입력 · 첫 결과 | **모바일 우선** — 카톡에서 열린다 |

**아이소크론 폐기는 유지한다.** 화면이 넓어져도 폐기 근거의 절반(위치를 다른 조건보다
과대 강조 — G10)은 그대로이고, 후보가 5개 고정이라 공간을 볼 이유가 없다는 것도 변하지 않는다.

## 매물 스냅샷 — 단계 1에서는 필요 없다

초안에서 스냅샷 저장을 크게 잡았다가 **범위를 줄였다.** 근거가 확실한 것이 하나뿐이다.

| 이유 | 근거 강도 |
|---|---|
| **현장 기록 보존** | ✅ **확실** — 방문해서 적은 것(수압·채광·소음·곰팡이, 중개사 답변)을 잃으면 안 된다 |
| 조건 변경 시 재판정 | ⚠️ 약함 — **살 수 없는 집을 재판정할 이유가 없다** |
| 지난 후보로 가격 감각 쌓기 | ⚠️ 약함 — 만들어낸 부가 가치. 사용자가 원한다는 근거 없음 |
| 성능 캐시 | ⚠️ 보류 — 최적화 문제이고 지금 판단할 단계가 아니다 |

### 그래서 단계별로 나뉜다

```
단계 1 (FT1~FT7)   스냅샷 불필요.  매물이 사라지면 그냥 제외한다
단계 2 (FT8·FT9)   현장 기록이 생기는 시점 → 이때 저장 문제가 실재한다
```

**단계 1에는 방문 후 기록이 아예 없다.** 사라진 매물에 붙어 있던 것은 판정 결과뿐이고,
그건 다시 계산하면 되는 값이다.

### 단계 2에서 정할 것

| 항목 | 내용 |
|---|---|
| 보존 대상 | **사용자가 만든 것만** — 현장 확인 기록 · 유지/보류/제외 · 중개사 답변 |
| 매물 정보는 | 그 기록을 이해하는 데 필요한 **최소 식별 정보**(주소·시점)까지만 |
| 표시 | `2026-08-19 기준 · 거래완료` — **시점과 상태를 함께.** 가격은 회색 처리 |
| 미정 | 보관 기간 · 관계 종료 시 처리(`09-edge-cases`와 같은 항목) |

> **가격을 스냅샷으로 보여줄 때가 가장 위험하다.** 현재가로 읽으면
> “이 정도면 되겠네”라는 잘못된 감각이 생긴다. 단계 2 설계 시 다시 확인한다.

## `확인 필요` 배지 강도 ✅ 결정

**확인 필요는 경고가 아니다.** 모른다는 것이지 나쁘다는 게 아니므로, 맥락에 따라 강도를 달리한다.

| 화면 | 강도 | 왜 |
|---|---|---|
| 후보 목록 (A-13) | **표시 안 함** 또는 아주 작게 | 판정 3분류를 흐리면 안 된다 |
| 상세 판정 (A-14) | **작은 인라인 `?` 배지** | “이건 자동 판정이 안 됨”만 알린다 |
| **방문 전 질문 카드 (A-17)** | **명확한 목록으로 크게** | **여기서는 행동을 유도해야 한다** |

- 색은 **neutral/info.** 경고색을 쓰지 않고, 미충족(warning)과 시각적으로 구분한다
- 둘 다 “✓가 아닌 것”이지만 성격이 다르다 — 하나는 못 채운 것, 하나는 모르는 것
- **개수 상한 없음** — 확인 항목은 판정에 안 들어가므로 판정을 흐리지 않는다. 쓸지 말지는 사용자 자유

# 1부 · 입력 설계 — 위밋플레이스에서 무엇을 빌려오나

`04-benchmarks.md`의 **“서비스 이름이 아니라 빌려올 메커니즘으로”** 를 실제로 적용한 기록.
참조를 가져올 때 **무엇이 딸려 오는지**까지 본다.

## 1. 구조 대조

| | 위밋플레이스 | 우리 |
|---|---|---|
| 후보를 | **생성한다** — 지도 전체가 후보 공간 | **판정한다** — 관심매물 5개 고정 |
| 조건이 | **1개** (위치) | **여러 개** (위치·예산·면적·주차) |
| 두 사람의 값이 | **같은 종류** — 둘 다 출발지 | **다른 종류 가능** — A는 통근, B는 면적 |
| 계산 방향 | **역방향** — 조건을 만족하는 지점을 찾음 | **순방향** — 주어진 지점을 평가 |
| 답이 | **하나의 최적 지점** | 판정 3분류. 최적 없음 |
| 입력 인터랙션 | **2~3회** | **7~10회** |

**세 번째가 결정적 차이다.** 위밋은 A·B가 같은 축에 값을 내므로 “중간”이 계산된다.
우리는 A가 통근 40분, B가 면적 66㎡를 내는데 **이 둘의 중간은 존재하지 않는다.**
그래서 위밋의 *계산*은 가져올 수 없고, *구조*만 가져올 수 있다.

---

## 2. 추상화하면 동형이다

```
위밋:  각자의 개인값(출발지) → 공통 공간(지도)    에 투영 → 겹침 → 후보
우리:  각자의 개인값(조건)   → 공통 공간(매물 5개) 에 투영 → 겹침 → 판정
                                      ↑
                              여기만 다르다
```

투영할 공통 공간이 **지도냐 매물 목록이냐**만 다르다.
`decisions/0003`(조건은 사람에 저장)이 이 구조의 전제이고, 위밋은 그 전제가
국내에서 이미 작동한다는 증거다.

---

## 3. 가져오는 것

### ① 투영 구조 — 단, 지도로 그리지는 않는다

각자의 값이 공통 공간에 투영되고 겹침을 본다는 **논리**는 가져온다.
`decisions/0003`(조건은 사람에 저장)이 그 전제이고, 위밋은 그 전제가 국내에서 작동한다는 증거다.

**그러나 그 공간을 지도로 그리지는 않는다.** 근거는 아래 「아이소크론을 폐기한 이유」에 한 번만 적는다.

### ② 입력 최소성 — 상대는 “자기 것”만 낸다

위밋에서 B는 출발지 하나만 낸다. 후보를 고르지도, 판단하지도 않는다.
우리도 같다 — **B는 매물을 담지 않고 자기 조건만 낸다.**
이미 설계에 있던 원칙이고, 위밋이 그 근거가 된다.

### ③ 결과의 즉시성

중간 확인 단계나 “제출” 버튼이 없다. 입력이 끝나면 바로 결과다.

---

## 4. 가져오면 안 되는 것 — 구조에 딸려 오는 것들

### ① 거리 합산 ⚠️ 가장 위험

위밋의 중간지점은 두 사람 이동시간의 **합 또는 최대값을 최소화**한 결과다.
**그게 곧 집계다.**

```
위밋:   min( A거리 + B거리 )        →  Additive Utilitarian
   또는  min( max(A거리, B거리) )    →  Least Misery
```

거리 구조를 가져오면서 이 계산이 따라 들어오면 `decisions/0001` 위반이다.
**우리 통근 조건은 각자의 임계값이지 합이 아니다.**

> **금지** — `A 34분 + B 22분 = 56분`, `평균 28분`, `합계 이동시간` 같은 값을
> 화면·계산·정렬 어디에도 만들지 않는다.

`05-tradeoff-patterns.md`에서 정리한 집계 전략이 **여기로 몰래 들어온다.**
참조를 가져올 때 가장 조심할 지점이다.

### ② 하나의 최적해

위밋은 “가장 공평한 지점”을 낸다. 단일 최적 개념이 있다.
우리가 그러면 총점이고, 05번에서 정리한 함정 ②(“우리 둘에게 **가장 좋은** 집”)로 되돌아간다.

### ③ 후보 생성

위밋은 지도에서 새 장소를 찾는다. 우리는 찾지 않는다 (G5 — 탐색으로 안 넓힌다).

### ④ 지도를 판정의 중심에 두기

**통근은 조건 4개 중 하나일 뿐이다.** 면적·주차는 지도에 그려지지 않는다.
지도를 메인으로 만들면 **위치가 다른 조건보다 중요해 보인다** — 강조 차등이라 G10 위반.

```
지도    위치 조건 전용 보조 화면 — ②에서 입력을 이해시키는 용도
판정    여전히 조건별 표 — ⑤
```

---

## 5. 입력 개수 격차 — 2~3회 vs 7~10회

이 격차가 H1의 실제 마찰이다. 위밋의 “하나 넣으면 끝”을 그대로 흉내 낼 수는 없지만,
**첫 결과까지의 거리**는 좁힐 수 있다.

### 채택: 점진적 공개 (progressive disclosure)

```
1단계   예산                          →  즉시 판정
        + 출근지 (출퇴근하면)             "5개 중 3개가 예산 안에 들어옵니다"
2단계   "더 좁히시겠어요?"            →  조건 추가
3단계   결과를 보고 필요하면          →  조건 더 추가
```

**입력 1~2개로 이미 결과가 나온다.** 근거가 셋이다.

| 근거 | 내용 |
|---|---|
| H3 완화 설계 | `02-hypotheses` — *“온보딩에서 한꺼번에 묻지 않는다. 출근지는 통근 시간을 볼 때, 대출 조건은 실질 비용을 볼 때 받는다”* |
| G8과 충돌하지 않음 | G8이 지키는 건 **처음 요구하는 입력 2번**이다. 필수 조건을 몇 개 덧붙이든 위반이 아니다 |
| 위밋의 감각 | 최소 입력으로 결과를 본 뒤 다듬는 흐름 |

### 대안과 비교

| 안 | 방식 | 판정 |
|---|---|---|
| **점진적 공개** | 2개 → 결과 → 추가 | **채택** — 첫 결과까지 가장 짧다 |
| 프리셋 기본값 | 필수조건에 흔한 값을 미리 선택 (“통근 40분 이하”) | **보조로 채택** — 단계마다 기본값을 두면 탭이 줄어든다 |
| 전부 한 화면 | 4개를 한 번에 | 기각 — 부담이 커 보이고 **이탈 지점을 못 잰다** |
| 대화형 입력 | 챗봇처럼 순차 질문 | 보류 — 탭 수는 비슷한데 구현 비용이 큼 |

### 이 결정이 바꾸는 것

| 문서 | 변경 |
|---|---|
| 14번 화면 ② | `4단계 순차` → **`2단계 필수 + 2단계 선택 확장`** |
| 15번 KPI | 완주율을 **2개 완료 / 3개 / 4개**로 나눠 측정 — 어디까지 채우는지가 H3의 실제 답 |
| `09-edge-cases` | **“필수 조건 0개 상태의 판정”** 이 새 경로로 추가됨 ↓ |

### 출근지는 없을 수 있다 ✅ 결정

초안은 출근지를 **1단계 필수**로 뒀다. **틀렸다.**

```
출근지가 없는 사람
  무직 · 구직 중 · 전업 · 프리랜서 · 전면 재택 · 은퇴 · 학생
```

이들에게 출근지를 요구하면 **첫 화면에서 막힌다.** 통근을 안 재는 게 아니라
**애초에 잴 대상이 없는 것**이고, 그건 결함이 아니라 정상 상태다.

> 하물며 **재택 근무자는 우리 1차 타깃과 크게 겹친다** — 30대 전월세 탐색자.
> 이 경로가 없으면 그 사람들이 첫 입력에서 이탈하고, 그건 H1 측정을 오염시킨다.
> 초대를 안 받은 게 아니라 **받고 나서 우리가 막은 것**인데 숫자로는 구분이 안 된다.

**그래서 항상 받는 것은 예산 하나뿐이다.**

| | 받는 시점 | 없으면 |
|---|---|---|
| **예산** | 1단계 · 항상 | — (없으면 판정할 게 없다) |
| **출근지** | 1단계 · **출퇴근하는 경우만** | 통근·교통비를 계산하지 않는다 |

화면 문구는 조건이 아니라 **질문**으로 낸다.

```
정기적으로 출퇴근하시나요?

  [ 네, 출근지를 넣을게요 ]     [ 아니요 / 재택이에요 ]
                                        ↓
                          통근 시간과 교통비를 계산하지 않습니다.
                          나중에 언제든 추가할 수 있어요.
```

*“출근지 (선택)”* 이라고 흐리게 두면 **빼먹은 것처럼 보인다.** 명시적으로 물어야
안 넣는 것이 정상 경로로 읽힌다.

### 그래서 판정에 무엇이 남나

1단계만으로 판정할 때는 **필수 조건이 없다.** 그래도 판정 3분류는 나온다.

| 상황 | 판정에 쓰는 것 |
|---|---|
| 둘 다 출퇴근 | **예산 + 각자의 통근** |
| 한 명만 출퇴근 | **예산 + 그 한 명의 통근** |
| 둘 다 출퇴근 안 함 | **예산만** |

**예산은 가구 총액이라 A·B의 금액이 같고 상한만 다르다.** 그래서 예산 하나만으로도
`한쪽만 충족`이 나온다 — A의 상한은 넘고 B의 상한은 안 넘는 매물이 생긴다.
**즉 출근지가 아무에게도 없어도 Hero Feature는 작동한다.**

다만 통근 임계값을 안 받았으므로 1단계에서는 **충족/미충족이 아니라 실제 값만** 보여주고,
조건이 들어온 뒤에 판정으로 전환한다.

| 단계 | 통근 표시 |
|---|---|
| 1단계 (임계값 없음) | `A 34분 · B 22분` — 값만 |
| 2단계 이후 (임계값 있음) | `A 34분 ≤ 40분 ✓` — 판정 |
| **출근지 없음** | **행 자체를 안 그린다** — `계산 안 함`도 쓰지 않는다 |

마지막 줄이 중요하다. `—`나 `계산 불가`를 넣으면 **빈칸이 결함처럼 보인다.**
`계산 불가`는 *“재려 했는데 실패했다”* 는 뜻이고(도서지역 등), **출근지 없음은 잴 것이 없는 것**이라 다르다.

### 비교표에서 통근 행은 둘 다 있을 때만 나란히 놓인다

*“예산과 통근은 둘 다 반드시 있으니 좌우로 비교된다”* 는 전제가 **통근에는 성립하지 않는다.**

| 누가 출퇴근하나 | 통근 행 |
|---|---|
| 둘 다 | A·B를 좌우로 나란히 |
| **한 명만** | **그 사람 칸만.** 반대쪽은 비우고 이유를 한 줄로 — `B는 출퇴근 안 함` |
| 아무도 안 함 | 행 없음 |

반대쪽을 비울 때 **빈칸만 두면 “입력을 안 했다”로 읽힌다.** 짧게 이유를 적는다.

## 6. 위밋플레이스 실사용 때 잴 것

`11-decision-status.md` §3 「외부 서비스 탐색」의 위밋플레이스 항목을 이 문서 기준으로 구체화한다.

| 측정 항목 | 왜 |
|---|---|
| 링크를 열고 입력을 끝낼 때까지 **탭 수** | Tier 0 카톡(3초)과 비교할 유일한 수치 |
| **가입을 요구하는 시점** — 있는가, 결과 전인가 후인가 | 우리 로그인 위치 결정 (F5 — 관심매물 조회에 로그인 필요) |
| 출발지 입력 UI — 검색인가 지도 탭인가 | ② 화면 |
| **결과를 총점으로 주는가 후보로 주는가** | 가져오면 안 되는 것 ①·② 확인 |
| 지도를 어디까지 쓰는가 (검색 확인용인가 범위 표시인가) | ② 화면 — 우리는 아이소크론을 폐기했다 |
| 한 명만 입력했을 때 화면 | **우리 `B 대기 중` 빈 경로의 직접 참조** |
| 상대가 안 들어오면 어떻게 되나 | 동일 |

**마지막 두 줄이 특히 중요하다.** 위밋도 우리와 같은 문제(상대가 안 들어옴)를 갖고 있고,
어떻게 처리하는지가 `decisions/0002`의 1인 빈 경로 설계에 직접 쓰인다.

## 7. 정리 — 참조를 가져오는 절차

이번 사례에서 실제로 쓴 순서다. 다른 참조 서비스에도 같은 절차를 쓴다.

```
1. 구조를 대조한다            무엇이 같고 무엇이 다른가

```

**4번이 이 절차의 핵심이다.** 좋아 보이는 것만 고르면 그 밑에 깔린

# 2부 · 시각화 명세 — 무엇을 어떻게 그릴 것인가

**형태를 먼저 정하고 색은 마지막에 정한다.** 대부분의 나쁜 차트는 색부터 고른다.

> **화면 파일** — `assets/joint-decision-ui.html`. 네이버 셸(헤더·좌측 네비) 안에
> 조건 대조 · 양보 지점 · 조건 완화 · 0건 재탐색 4화면. 375 / 768 / 1400 검증 완료.

## 0. 시각 위계 — 안내문보다 판정이 커야 한다 ✅ 결정 (2026-08-20)

프로토타입 검토에서 나온 문제다. **설명이 크고 정작 볼 것이 작았다.**

```
✗  "순위나 종합점수 없이, 누가 어떤 조건을 감수하는지 보여드립니다"   ← 크고 진하다
   +3분  ? 확인                                                    ← 10px, 회색
```

사용자가 화면에서 실제로 쓰는 값은 **미달량과 판정 상태**다. 안내문은 한 번 읽고 다시 안 본다.
**한 번 읽는 것이 매번 보는 것보다 크면 위계가 뒤집힌 것이다.**

### 크기 순서를 고정한다

| 순위 | 무엇 | 대략 |
|---|---|---|
| 1 | **판정 상태 + 미달량** (`+3분` · `✓ 충족` · `? 확인`) | **14~16px, 굵게** |
| 2 | 매물 이름 · 실부담 금액 | 16~18px |
| 3 | 조건 값 (`13분 > 10분`) | 14px |
| 4 | 양보 문장 | 15px |
| 5 | **안내·설명문** | **12~13px, 보조색** |

**배지는 장식이 아니라 판정 결과다.** 12px 이하로 내리지 않고, 아이콘·라벨·색 셋을 함께 쓴다.

### 안내문은 접거나 한 번만 보여준다

같은 안내를 화면마다 반복하면 그만큼 판정이 밀려난다.

| 안내 | 어디에 |
|---|---|
| “총점을 내지 않습니다” | **상단 배너 한 번.** 각 화면에 반복하지 않는다 |
| “사진을 숨겼습니다” | 해당 영역 하단에 12px 보조문 |
| “전제 보기” | **접어둔다.** 펼치면 금리·기회비용률 근거 |

## 1. 원칙 — 시각화가 몰래 총점을 만들 수 있다

가장 큰 위험은 화면에 `%`가 없어도 **면적·길이·거리가 종합 점수로 읽히는 것**이다.
`decisions/0001`은 숫자만 금지한 게 아니라 **합산 자체**를 금지한다.

| 형태 | 왜 위험한가 | 판정 |
|---|---|---|
| **레이더 / 스파이더 차트** | 조건 5개를 축으로 그리면 **면적이 곧 총점**이다. 그리고 축 순서만 바꿔도 면적이 달라진다 | **금지** |
| **A·B를 겹친 레이더** | 누가 더 만족하는지가 면적 비교로 읽힘 → 편들기 (G10) | **금지** |
| **종합 게이지 · 도넛** | 하나의 값으로 뭉침 | **금지** |
| **후보 순위 리스트** | 정렬 자체가 랭킹 | **금지** |
| **별점 · 하트 개수** | 척도가 곧 점수 | **금지** |
| **누적 막대로 조건을 쌓기** | 총 길이 = 합산 | **금지** |
| **이중 축** (통근 시간 + 비용을 한 차트에) | 두 척도를 겹치면 아무 관계나 만들어 보임 | **금지** |

> **판정 규칙** — 조건 여러 개가 **하나의 도형·길이·면적으로 합쳐지면 위반.**
> 조건은 언제나 **각각 따로** 표현하고, 옆에 나란히 둘 뿐 더하지 않는다.

## 2. 색 규칙 — 두 체계가 충돌하고 있다

지금 설계에는 색이 하는 일이 둘이고, 서로 싸운다.

```
identity   A / B 를 구분          → 사람
status     충족 / 미충족 / 확인   → 판정
```

**한 화면에 둘 다 색으로 쓰면 무엇이 무엇인지 알 수 없다.**
A가 초록이고 충족도 초록이면, 초록 점이 "A"인지 "충족"인지 매번 헷갈린다.

### 결정

| | 무엇으로 구분하나 |
|---|---|
| **A / B (identity)** | **위치 + 라벨.** 색을 쓰지 않는다 |
| **충족 / 미충족 / 확인 필요 (status)** | **색 + 아이콘 + 라벨.** 색은 여기에만 |

두 가지 이유다.

**① status가 이 화면의 핵심 정보다.** 사용자가 알고 싶은 건 "A의 것"이 아니라 "되는가 안 되는가"다.
**② A/B에 다른 색을 주면 그 자체가 차등이 될 수 있다.** IPDAS의 *주의 조작 금지* — 강조 차등이 편향을 만든다(G10).
   좌우 배치와 동일한 크기·같은 서체가 균형을 보장한다.

> **주의** — 발표 문서(`assets/reverse-planning.html`)에서는 A=틸, B=플럼으로 색을 줬다.
> 그건 **읽는 문서**라 identity가 핵심이기 때문이고, **제품 화면은 반대**다.
> 문서의 색 선택을 제품에 그대로 옮기지 않는다.

#### 네이버 그린은 상태색으로 쓸 수 없다 ✅ 결정 (2026-08-20)

**측정값이 결정했다 — `#03C75A`는 흰 배경 대비 2.25:1로 WCAG AA에 실패한다.**
글자나 작은 UI에 못 쓰고, 흰 글씨를 얹어도 마찬가지다.

그리고 더 큰 문제가 있다. **네이버가 이미 초록을 액션·활성 상태에 쓴다.**
우리가 `충족`에도 초록을 쓰면 같은 화면에서 초록이 두 가지를 뜻하게 된다.

| 역할 | 색 | 대비 |
|---|---|---|
| 브랜드·활성 네비 | `#03C75A` | 로고와 네비 배경에만. **글자를 얹지 않는다** |
| 우리 액션 버튼 | `#00873C` | 흰 글씨 4.63:1 ✅ |
| **충족** | 회색 `#3F4A5A` / bg `#EEF1F4` | 7.92:1 ✅ |
| **미충족** | 주황 `#B3400C` / bg `#FFF1E6` | 5.19:1 ✅ |
| **확인 필요** | 파랑 `#1D4ED8` / bg `#EAF0FE` | 5.87:1 ✅ |
| 둘 다 불충족 | `#5F6B7A` / bg `#F3F5F7` | — |

**충족에 초록을 안 쓰는 두 번째 이유가 더 중요하다 — 충족은 조용해야 한다.**
대부분의 조건은 충족이라, 충족이 강한 색이면 화면이 그 색으로 뒤덮이고
**정작 봐야 할 미충족이 묻힌다.** 사용자가 찾는 것은 `✓`가 아니라 `✕ +3분`이다.

색맹 분리도 검증했다 — 최악 인접쌍 ΔE 18.3(deutan) / 18.7(normal)로 기준(8/15)을 넘는다.
그래도 **색 단독으로 상태를 전하지 않는다** — 아이콘 + 라벨 + 색 셋을 항상 함께 쓴다.

### 예외 하나 — 지도의 경로선 ✅ 결정

지도에 A·B의 통근 경로를 함께 그리면 **둘을 구분할 수단이 색밖에 없다.**
위치도 라벨도 겹치기 때문에 identity에 색을 쓰지 않는다는 규칙이 여기서는 성립하지 않는다.

| 영역 | A/B 구분 | 왜 |
|---|---|---|
| 판정 영역 (④ 목록 · ⑤ 상세 · ⑦ 비교표) | **위치 + 라벨.** 색 금지 | 원칙 그대로 |
| **지도의 경로선** | **색 허용** | 겹치는 선을 라벨로 못 가른다 |

**단 조건이 둘이다.** ① 두 경로의 **선 굵기·투명도를 같게** 한다(강조 차등 금지 — G10)
② 지도 밖으로 그 색을 가져가지 않는다. 판정 영역에서는 여전히 `A ✓ B ✓` 라벨만 쓴다.

### status 색은 예약한다

| 상태 | 역할 | 아이콘 필수 |
|---|---|---|
| 충족 | good | ✓ |
| **미충족** | **warning** — critical이 아니다 | ✗ |
| 확인 필요 | neutral/info — **경고가 아니다** | ? |
| 둘 다 불충족 | muted (후보에서 내려감) | — |

#### `확인 필요` 배지 강도는 맥락에 따라 다르다 ✅ 결정

| 화면 | 강도 | 왜 |
|---|---|---|
| 후보 목록 | **표시 안 함** 또는 아주 작게 | 판정 3분류를 흐리면 안 된다 |
| 상세 판정 | **작은 인라인 `?`** | “자동 판정이 안 됨”만 알린다 |
| **방문 전 질문 카드** | **명확한 목록으로 크게** | **여기서는 행동을 유도해야 한다** |

**개수 상한을 두지 않는다.** 확인 항목은 판정에 들어가지 않아 판정을 흐릴 수 없다.
초안의 상한 3개는 확인 항목이 판정에 섞이던 시절의 규칙이라 근거가 사라졌다.

**미충족을 빨강(critical)으로 쓰지 않는다.** 조건을 못 채운 건 오류가 아니라 협상 지점이다.
빨강을 쓰면 "이 집은 틀렸다"로 읽혀 `한쪽만 충족`을 후보로 유지하려는 설계와 싸운다.

**확인 필요를 경고색으로 쓰지 않는다.** 모른다는 것이지 나쁘다는 게 아니다.

색은 **절대 단독으로 상태를 전달하지 않는다** — 항상 아이콘 + 라벨과 함께.

## 3. 화면별 — 사용자의 질문에서 형태를 고른다

### ② 내 조건 입력

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| 지금 몇 번째지, 얼마나 남았지 | 2단계 진행 표시 | **스텝 인디케이터** |
| **40분이면 대체 어디까지지?** | **내 후보 5개의 실제 시간을 바로 보여줌** | — (차트가 아니다) |
| 66㎡가 감이 안 온다 | 기존 거주지·아는 평형과 비교 | **레퍼런스 마커** |

### 아이소크론을 폐기한 이유

초안에서는 출근지 기준 도달 범위를 지도에 칠하는 **아이소크론(isochrone·등시선)**을
이 화면의 핵심으로 뒀다. **모바일 검토에서 폐기했다.**

| 문제 | 내용 |
|---|---|
| 형태가 안 읽힌다 | 등시선은 대중교통 노선을 따라 **삐죽삐죽 뻗은 불규칙한 형태**다. 작은 화면에서 윤곽 자체가 판독되지 않는다 |
| 겹치면 더 어렵다 | 두 개를 겹치면 색이 섞여 어디가 교집합인지 구분이 안 된다 |
| 조작 부담 | 확대·축소가 필요한데, **입력 단계에서 그건 마찰**이다 |
| **강조 차등** | 입력 화면에서 지도를 크게 쓰면 **위치가 다른 조건보다 중요해 보인다** — G10 |

그리고 더 근본적인 이유가 있다. **아이소크론은 위밋플레이스의 필요이지 우리 필요가 아니었다.**

```
위밋:  후보를 찾아야 한다     →  공간 전체를 봐야 한다  →  지도가 필수
우리:  후보가 이미 5개 있다   →  그 5개만 보면 된다     →  지도가 왜 필요한가
```

“40분이 어느 정도인지”를 **추상적 범위로 보여줄 이유가 없다.** 내 후보의 실제 시간으로 답한다.

```
✗  지도에 40분 영역 칠하기
✓  상도동 28분 · 흑석동 34분 · 신길동 52분
```

점진적 공개로 **입력 직후 바로 결과가 나오므로**(1부 §5),
그 결과가 곧 범위 설명이다. 별도 시각화가 필요 없다.

#### 조건 모순(A-13c)도 지도 없이 설명된다

```
두 분 조건을 동시에 만족하는 후보가 없습니다.

  A · 강남역 20분 이내      가장 가까운 후보: 상도동 28분  (+8분)
  B · 여의도역 20분 이내    가장 가까운 후보: 신길동 14분  ✓

  같은 집이 두 조건을 다 만족하지는 못합니다.
```

**“서울에 그런 곳이 없다”고 주장하지 않는다** — 근거가 없다.
우리가 말할 수 있는 건 **“이 5개 중에는 없다”** 뿐이고 그게 정확한 진술이다.

### 지도의 역할 — 두 가지까지 ✅ 결정 (2026-08-20 확장)

초안은 **“출근지 검색 확인용만”** 으로 좁혔다. 프로토타입 대조에서 **하나를 더 열었다.**

| 용도 | 채택 | 이유 |
|---|---|---|
| ② 출근지를 고를 때 검색 결과 확인 | ✅ | 초안부터 |
| **후보 5개를 지도에 찍고 판정 색으로 칠하기** | ✅ **추가** | 아래 |
| 조건 범위(아이소크론)를 칠하기 | ✗ **폐기** | 위 참조 |

**판정 핀은 G10 위반이 아니다.** 아이소크론과 방향이 반대이기 때문이다.

```
아이소크론   조건 범위를 그린다  →  위치가 판정을 만든다     →  위치 과대 강조
판정 핀      이미 나온 판정을    →  위치에 얹는다            →  위치는 부가 정보
             색으로 표시
```

판정은 여전히 **좌측 리스트에서 나오고**, 지도는 *“그래서 이것들이 어디 있나”* 만 덧붙인다.
지도를 판정의 **중심에 두면** 그때는 G10 위반이다 → 이 문서 1부 §4-④.

### ④ 후보 목록

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| 5개 중 뭐가 살아있나 | 3분류 그룹 헤더 + 개수 | **그룹 카운트** |
| 이건 왜 여기 있지 | 카드에 미달 요약 한 줄 | **인라인 배지** |
| 어느 게 아깝나 | **미달량이 작은 순으로 정렬** | — |

`한쪽만 충족` 그룹 안에서는 **미달량이 작은 것을 위에 둔다.** 종합 순위가 아니라
"조금만 양보하면 되는 것"을 앞에 두는 것이라 총점이 아니다. 정렬 기준을 화면에 밝힌다.

### 조건 표시 순서 — 시각 흐름과 IPDAS를 같이 만족시킨다 ✅ 결정

IPDAS는 **개인 가치 우선 순서**(중요 속성을 먼저)를 권하고, 그것이 가치일치 선택을
70% → 90%로 올린다(F10). 동시에 **A와 B의 항목 순서가 같아야** 좌우 비교가 된다.

**그런데 A와 B는 서로 다른 조건을 고른다.** 순서를 그대로 맞출 수 없다.
그래서 **조건 종류로 고정 정렬**한다.

```
1  예산        ← 항상 있음. 값도 같음(가구 총액), 상한만 다름
2  통근시간    ← 출퇴근하는 사람만. 없으면 행 자체가 없다
─────────────  여기까지가 항상 나란히 비교된다
3  각자의 필수 ① ~ ④   ← 사용자가 넣은 만큼. 0개일 수도 있다
─────────────
4  확인 필요   ← 판정 안 함. 맨 아래

선호는 이 표에 들어오지 않는다 — 매물에 붙지 않고 사람에 붙는다(상단 카드)
```

| 결정 | 이유 |
|---|---|
| **예산·통근을 위에** | 둘 다 반드시 있으므로 **같은 행에서 좌우 비교**가 성립한다 |
| 각자의 필수는 그 아래 | 서로 다른 항목이라 비교가 아니라 나열이다 |
| **미충족을 위로 올리지 않는다** | 정렬이 사람마다 달라져 **비교가 깨지고**, “문제부터 보여주기”가 부정 프레임이 된다 |
| 확인 필요는 맨 아래 | 판정에 들어가지 않으므로 |

#### 화면 전체의 세로 흐름

사용자는 위에서 아래로 **“판정 → 왜 → 그래서 뭘 할 수 있나”** 순으로 읽는다.

```
1  판정 결과      한쪽만 충족 · B 충족 / A 미충족      ← 결론부터
2  조건 대조      위 순서대로, A/B 좌우 동일 비중        ← 근거
3  양보 문장      "A가 3분 더 걷습니다. 대신…"          ← 해석
4  완화 제안      양쪽 안을 동시에                      ← 행동
5  확인 항목      방문 전에 물어볼 것                    ← 보류된 것
```

**결론을 맨 위에 두는 것**은 스캔하는 사용자가 목록으로 돌아갈 때 판정만 보고 넘어갈 수
있어야 하기 때문이고, **행동(완화)을 아래에 두는 것**은 근거를 읽기 전에 조건부터
바꾸게 만들면 안 되기 때문이다.

### ⑤ 매물 상세 판정 ★

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| **얼마나 모자란 거지?** | **임계값과 실제값을 한 줄에 나란히 쓰기** | **텍스트 대조** ★ |
| 나랑 상대가 뭐가 다른 거지 | 두 값을 선으로 잇기 | **덤벨 차트(dumbbell)** |
| 이 집이 뭐가 나은데 | 5개 후보 중 위치를 점으로 | **점 플롯(dot plot) · 스트립 플롯** |

#### 불릿 차트에서 텍스트로 바꿨다 ✅ 결정 (2026-08-20)

초안은 **불릿 차트(bullet chart)** 를 이 화면의 답으로 잡았다. 프로토타입 대조에서 뒤집혔다.

```
✗  역 도보   ├────────────┼──▓──┤   13분  ✗ +3분
✓  역 도보   13분 > 10분  ✗ +3분
   통근      34분 ≤ 40분  ✓
   실부담    128만 ≤ 130만 ✓
```

| | 텍스트 | 불릿 차트 |
|---|---|---|
| 정확도 | **정확한 값이 보인다** | 길이는 근사 |
| 미달량 | `+3분` 숫자 | 숫자 + 길이 |
| **조건 5~6개를 쌓으면** | **밀도가 높고 스캔이 빠르다** | 세로로 길어진다 |
| 구현 | 즉시 | 스케일 기준 설계 필요 |

**결정적인 이유는 공통 축이 없다는 것이다.** 조건마다 단위가 다르다(분·㎡·만원·개).
축을 공유하지 못하면 **길이 비교가 아무 의미도 만들지 못하고**, 화면만 무거워진다.

**불릿 차트는 폐기가 아니라 용도 축소다.** 조건 **하나**를 강조할 때는 여전히 최선이다 —
⑥ 완화 시뮬레이션의 슬라이더 구간이 그 자리다(거기서는 축이 하나뿐이다).

"이 집이 뭐가 나은데"에는 **점 플롯**이 답한다. 5개 후보의 통근 시간을 한 줄에 점으로 찍고
이 매물만 강조하면, **총점 없이도 상대 위치**가 보인다.

```
통근시간   ●    ●  ◉      ●        ●
          22   28  34    45       52     ← ◉ 가 이 매물. 5개 중 3번째
```

### ⑥ 조건 완화 ★★

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| **얼마나 풀면 뭐가 달라지지?** | 핸들을 끌면 결과가 실시간 변화 | **제약 완화 미리보기 (constraint relaxation preview)** ★ |
| 등급이 어떻게 옮겨가지 | 완화 전/후를 선으로 연결 | **슬로프 그래프(slope graph)** |
| 어느 조건을 푸는 게 이득이지 | 조건별 효과를 나란히 | **다이버징 바** 또는 **정렬된 바** |

**이 화면이 가장 중요하고 가장 어렵다.** 핵심은 **드래그하는 동안 결과가 따라 움직이는 것**이다.

```
A · 역 도보     10분 ────●──── 13분        [드래그 중]
                             ↑
                        여기까지 풀면

  둘 다 충족   1 ━━━━━━▶ 3        (+2)
  한쪽만       3 ━━━━━━▶ 1
  둘 다 불충족 1 ━━━━━━▶ 1
     ↑ 슬로프 그래프 — 두 상태를 선으로 연결
```

**양쪽 완화안을 항상 같이 보여준다(G1).** 슬라이더도 A용·B용 둘을 동시에 놓는다.
하나만 있으면 그 사람이 양보하라는 뜻이 된다.

### ⑦ 방문 후보 확정

| 사용자의 질문 | 형태 | 용어 |
|---|---|---|
| 최종 2개를 어떻게 비교하지 | 행=조건, 열=매물, 점수 없음 | **비교 표 (Option Grid 형식)** |
| 실부담 차이가 어디서 나지 | 항목별 증감을 누적으로 | **워터폴 차트** |

```
                 후보 A      후보 B
 A 통근          34분 ✓      52분 ✗ +12분
 A 역도보        13분 ✗ +3분  7분 ✓
 B 전용          68㎡ ✓      59㎡ ✗ −7㎡
 B 주차          있음 ✓      있음 ✓
 실부담          128만       121만
 반려동물        ? 확인      ? 확인
```

**총점 행이 없다.** 이게 Option Grid를 그대로 따르는 지점이다.

**워터폴**은 "왜 이 집이 7만원 싼가"에 답한다.

```
후보A 128만 ┃
  월세        −5만  ▼
  관리비      +2만  ▲
  교통비      −4만  ▼   ← B의 통근이 짧아져서
후보B 121만 ┃
```

### ⑧ 방문 후 기록

| 사용자의 질문 | 형태 |
|---|---|
| 뭘 확인해야 하지 | 체크리스트 |
| 둘 다 봤나 | **완료 상태 2개를 나란히** — 진행률 아님 |

## 5. 참조 서비스 — 직접 볼 것

**각 항목에 "무엇을 볼지"가 붙어야 탐색이 감상으로 끝나지 않는다.**

### A. 제약 완화 미리보기 — ⑥의 직접 참조 ★★

우리 FT6과 **구조가 같은** 기능을 이미 하는 곳들이다. 여기가 가장 중요하다.

| 서비스 | 어디를 볼까 | 무엇을 볼까 |
|---|---|---|
| **스카이스캐너** | 항공권 검색 → **“가장 저렴한 날짜”·±3일 달력** | **조건(날짜)을 풀면 결과가 어떻게 변하는지 보여주는 방식.** 우리 완화와 논리가 동일 |
| **아고다 / 부킹닷컴** | 숙소 필터 사이드바 | **필터 옆의 “(+34)” 표기** — 이 필터를 풀면 몇 개가 늘어나는지 미리 보여줌 |
| **에어비앤비** | 필터 → 결과 0건일 때 | **막다른 길 처리** — “필터를 지우면 N개” 안내. 우리 `전부 불충족` 화면의 직접 참조 |
| **호갱노노** | 지도 필터 조작 | **드래그하는 동안 지도가 실시간으로 반응하는 속도감.** 국내 부동산 최고 사례 |
| **네이버 항공권** | 최저가 달력 | 완화 결과를 달력 격자로 보여주는 방식 |

> **핵심 관찰 포인트** — 이들은 전부 **“조건을 풀면 +N개”**를 보여준다.
> 우리는 개수가 아니라 **등급 이동**을 보여줘야 한다(후보가 5개뿐이라).
> 같은 논리를 다른 출력으로 옮기는 게 설계 과제다.

### B. 불릿 차트 · 임계값 표현 — ⑤

| 서비스 | 어디를 볼까 | 무엇을 볼까 |
|---|---|---|
| **토스 · 뱅크샐러드** 신용점수 | 점수 화면 | **반면교사.** 게이지로 단일 점수를 보여주는 전형. 우리가 피할 형태 |
| **애플 건강 / 삼성 헬스** | 일일 목표 대비 | 목표선과 실제값을 한 줄에 놓는 방식 |
| **Datadog · Grafana** SLO 대시보드 | 공개 데모 | 불릿 차트 원형. 임계값 마커가 어떻게 생겼는지 |
| **당근 · 번개장터** 가격 필터 | 가격 범위 슬라이더 | 범위와 현재값을 같이 보여주는 방식 |

### C. 비교 표 — ⑦

| 서비스 | 어디를 볼까 | 무엇을 볼까 |

#### 로그인을 뒤로 미룬다 ✅ 결정

초안에서는 진입 직후 로그인을 요구했다. F5(관심매물 조회에 로그인 필요)를 근거로 삼았는데,
**적용을 잘못했다.**

```
F5:  "A의 관심매물 목록" 조회에 로그인이 필요하다
       ↓
      그런데 B는 A의 관심매물 목록을 조회하는 게 아니다
      A가 고른 후보 5개를 보는 것이다
```

**A의 관심매물 목록**(개인 데이터)과 **A가 공유한 후보 묶음**(별도 객체)은 다르다.
후보를 선택하는 순간 공유 객체가 만들어지면, B는 그것을 보는 것이지 A의 계정 데이터에
접근하는 것이 아니다.

```
초대 진입 → 후보 미리보기 → 조건 입력 → 결과 확인 → [저장하려면 로그인]
                                                        ↑
                                        B가 이미 값을 본 뒤에 요구한다
```

**H1 깔때기에서 로그인이 조건 입력 뒤로 밀린다.** 지금까지 “우리가 못 고치는 구간”으로
뒀던 H1-b가 상당 부분 우리 손에 들어온다.

| 남은 제약 | 상태 |
|---|---|
| 비로그인 페이지를 만들 수 있는가 | **네이버 정책 — 우리가 정할 수 없다.** 확인 필요 |
| B가 로그인 안 하면 입력한 조건을 어디 두나 | ✅ **결정** — 초대 코드에 묶어 서버 임시 저장(마지막 접근 +30일) |

#### 링크와 코드 — 대안이 아니라 보조 관계

| | 링크 | 코드 |
|---|---|---|
| 진입 | **클릭 한 번** | 앱·웹 진입 + 코드 입력 = 두 단계 |
| 전달 채널 | 카톡 · 문자 | **말로도 전달 가능** |
| 유실 시 | 다시 보내야 함 | **재진입 가능** |
| 선행 사례 | 위밋플레이스 | **특별시 6자리**(F3) |

**기본은 링크, 보조로 코드.** 코드 자체가 로그인을 우회하는 것은 아니다 —
우회는 위의 **공유 객체 분리**가 한다.

> **B-02가 중요하다.** 조건을 묻기 **전에** 무엇을 하는 자리인지 보여줘야 한다.
> CJM에서 B의 감정은 첫 접점부터 낮다 — 맥락 없이 입력부터 요구하면 거기서 끊긴다.

## 아직 열려 있는 질문 다섯

### ① 회차는 2~3번 반복된다 ✅ 결정

실측은 **총 방문 3.5~4.3개**(H5)인데 종료점은 2개다. 모순이 아니라 **단위가 다르다** —
2개는 “한 번 나갈 때 보는 수”, 4개는 “계약까지 총합”이다.

```
전체 여정 2.5개월 · 총 4.1곳 방문

  1회차   후보 5개 → 2개 보러 감 → 둘 다 제외 → 다시
  2회차   후보 5개 → 2개 보러 감 → 하나는 보류 → 다시
  3회차   ...
                              총 4~6곳 보고 계약
```

**우리 서비스는 한 번 쓰고 끝나는 게 아니라 2~3번 반복된다.**

| 함의 | 내용 |
|---|---|
| **재진입이 정상 경로다** | 1회차 방문 후 둘 다 제외되면 다시 담고·판정하고·정한다 (A-18c → A-20) |
| **2회차는 입력이 0번이다** | 조건이 사람에 저장돼 있어 새 매물을 담으면 **자동 판정**된다 (A-20b). `decisions/0003`의 값어치가 실제로 드러나는 지점 |
| **방문하면 조건이 바뀐다** | “생각보다 좁네”, “역세권이 이렇게 중요한 줄 몰랐네” — 조건 수정 경로가 상시 필요하다 ↓ |
| 리텐션 지표 | “재방문율”이 아니라 **“2회차 진입률”** |

#### 조건 수정은 상시 접근 창 하나로 해결된다

“방문 후 조건 조정”을 별도 경로로 만들 필요가 없다. **내 조건 화면(A-19)에 언제든
들어갈 수 있으면 된다.** 진입점만 여러 곳에 둔다.

| 진입점 | 위치 |
|---|---|
| 상시 | 헤더·설정 — 어느 화면에서든 |
| 결과를 보고 | 후보 목록(A-13)에서 “내 조건 보기” |
| 막다른 길에서 | 전부 불충족(A-13b)에서 “조건 다시 보기” |
| **방문 후** | 현장 기록(A-18)에서 “조건 바꾸기” |

수정하면 **전체가 즉시 재판정**되고(A-19a 영향 미리보기), 상대에게 알림이 간다(A-19b).
회차가 반복되는 구조에서는 이 창이 **재진입의 실질적 시작점**이 된다.

### ② 선택은 비동기다 ✅ 결정

A가 고르고 며칠 뒤 B가 고를 수 있다. 처리는 **알림 + 즉시 반영**으로 한다.

| 항목 | 결정 |
|---|---|
| 선택 유효기간 | **두지 않는다** — 만료 처리라는 상태가 하나 더 생기는데 얻는 게 없다 |
| 상대가 선택하면 | **알림** — “상대가 보러 갈 집을 골랐어요” |
| **매물이 빠지면** | **즉시 제외 + 알림** — 유효기간이 아니라 **매물의 실재 여부**가 기준이다 |
| 정한 후보가 빠지면 | 한 자리가 비므로 **A-16e(남은 한 자리)로 자동 복귀** |

유효기간을 대신하는 것이 **매물 소진 감지**다. 시간이 아니라 대상이 사라지는 것이 진짜 만료다.

### ③ “합의”라는 말을 쓰지 않는다 ✅ 결정

내부 용어로만 쓴다. 화면에는 **“이번에 보러 갈 집 정하기”**.

### ④ 전부 불충족(0건)의 분기 ✅ 결정

`전부 불충족`(A-13b)일 때 길이 둘이다.

```
a)  조건 완화       기존 5개 중에서 살린다
b)  재탐색          네이버로 돌아가 새 매물을 찾는다
```

**지금까지는 a만 있었다.** 그런데 **완화를 먼저 들이대면 “네 기준을 낮춰라”가 된다.**
조건이 문제인지 후보가 문제인지를 먼저 갈라야 한다.

#### 판별 — 임계선을 만들지 않고 계산으로 가른다

미달량은 조건마다 단위가 다르다(`+12분`, `−7㎡`, `+월 15만`). 이걸 비교하려고
정규화하면 **그게 곧 집계이고 `0001` 위반**이다. 그래서 **완화 시뮬레이션을 실제로 돌려본다.**

```
각 조건에 대해 "실제 미달량만큼 풀면 몇 개가 살아나는가"를 계산한다
  (완화폭은 임의값이 아니라 FT6이 이미 쓰는 실제 미달량)

  1개 조건만 풀어서 살아나는 매물이 있다   →  (a) 완화 제안
  어떤 조건 하나를 풀어도 안 살아난다      →  (b) 재탐색 제안
```

**“2개를 동시에 풀면?”은 계산은 되지만 제안하지 않는다.** 조건 두 개를 낮추라는 말이
되어 G1의 편들지 않기를 넘어선다.

한 조건만 풀어서 안 살아난다는 것은 **매물마다 2개 이상의 조건을 미달한다**는 뜻이고,
그건 조건이 빡빡한 게 아니라 **후보가 안 맞는다**는 신호다.

#### 화면

```
(a) 완화 가능
    "A가 역 도보를 13분까지 허용하면 2개가 살아납니다"
    "B가 전용면적을 59㎡까지 허용하면 1개가 살아납니다"
    → A-15 조건 완화

(b) 완화 불가
    "지금 후보 5개는 두 분 조건과 여러 항목에서 떨어져 있습니다.
     조건 하나를 푸는 것만으로는 살릴 수 없어요."

    [ 다른 매물 찾아보기 ]      [ 내 조건 다시 보기 ]
         → 네이버 탐색              → A-19
```

**(b)에서도 우리가 “낮추세요”라고 말하지 않는다.** 선택지만 놓는다.

#### 재탐색은 “네이버 필터를 다시 거는 일”이다

여기에 중요한 사실이 하나 있다. **후보 5개는 이미 네이버 필터를 통과한 것들이다.**
사용자는 탐색할 때 거래유형·매물유형·가격·면적·단지·역세권 등으로 이미 한 번 걸렀다.

> **그런데 전부 불충족이 나왔다면, 네이버 필터와 우리 조건이 어긋나 있다는 뜻이다.**

```
네이버 필터   전세 3억 이하 · 아파트                 ← 면적 조건이 없었다
우리 조건     실부담 130만 이하 · 전용 66㎡ 이상
                                   ↑
후보 5개가 전부 면적 미달 — 애초에 66㎡ 필터를 안 걸고 찾았기 때문
```

따라서 재탐색 제안은 “다시 찾아보세요”가 아니라 **“필터를 이렇게 바꿔서 찾으세요”** 여야 한다.
선택지를 더 정확히 좁히는 것은 그쪽이다.

#### 필터 제안 화면

| 조건 | 필터로 넘기나 | 어떻게 |
|---|---|---|
| 예산 | ✅ | 두 사람 중 **더 낮은 상한** |
| 전용면적 | ✅ | 더 **높은 하한** |
| 역 도보 | ✅ | 더 짧은 쪽 (역세권 필터) |
| 주차 | ✅ | 한 명이라도 필요하면 필요 |
| 매물 유형 | ✅ | 두 사람이 같은 유형을 원할 때만 |
| **통근시간** | ❌ | **출근지가 각자 달라 필터 하나로 표현할 수 없다** |
| 거래유형 · 매물유형 | — | **우리 조건이 아니다.** 사용자가 건 것을 그대로 둔다 |

```
┌────────────────────────────────────────────┐
│  이렇게 찾으면 두 분 조건에 더 가까워요      │
│                                            │
│   지금 필터            바꿀 필터            │
│   전세 3억 이하    →   전세 3억 이하  (유지) │
│   아파트           →   아파트        (유지) │
│   면적 —           →   전용 66㎡ 이상  ← B   │
│   역세권 —         →   도보 10분 이내  ← A   │
│                                            │
│   이 조건으로 매물 34개                     │
│                                            │
│   [ 이 필터로 찾아보기 ]   [ 그냥 찾기 ]     │
│                                            │
│   ※ 통근 조건은 필터에 없지만 저장돼 있어서,  │
│      새로 담는 매물에 바로 적용됩니다.        │
└────────────────────────────────────────────┘
```

**필터를 우리가 자동으로 걸지 않는다.** 제안하고 사용자가 적용한다 —
필터도 결정이고, G1(AI가 고르지 않는다)이 여기까지 적용된다.
`[ 그냥 찾기 ]`를 나란히 두는 이유이기도 하다.

#### 결과 수 미리보기 ✅ 채택

`이 조건으로 매물 34개` — 아고다·에어비앤비의 `(+34)` 패턴이다. 채택 이유가 셋이다.

| 이유 | 내용 |
|---|---|
| **적용 전에 판단할 수 있다** | 34개면 넉넉하고 2개면 너무 좁다는 것을 눌러보기 전에 안다 |
| **필터가 과한지 알려준다** | 0~3개가 나오면 **조건이 아니라 필터가 문제**라는 신호 |
| 이미 있는 계산이다 | 네이버 검색 결과 수는 별도 계산이 아니다 |

**0개일 때는 제안 자체를 하지 않는다.** “이 필터로 찾으면 0개입니다”는 제안이 아니라
막다른 길이므로, 그때는 **어느 조건이 결과를 0으로 만드는지**를 짚어준다.

#### 흐름 연결

```
A-13b 전부 불충족
   ├─ (a) → A-15 완화 → 후보 생김 → A-16 정하기
   └─ (b) → 네이버 탐색 → A-20 매물 추가 → 자동 판정 → A-13
                                                  └─ 회차 반복 구조와 같은 경로
```

### ⑤ 확정 후 취소는 별도 기능이 아니다 ✅ 결정

초안에서는 예약 도메인(호텔·항공)의 취소 패턴을 참조해 undo 배너·부분 취소·확인창을
검토했다. **과했다.**

> **호텔·항공 취소는 돈과 자리가 걸려 있어 무겁지만, 우리는 아직 아무것도 예약하지 않았다.**
> 후보 목록을 고친 것뿐이다.

1부 §7의 *“참조를 가져올 때 딸려 오는 것을 찾는다”* 가
여기서도 걸렸다 — 이번에 딸려 온 것은 **예약 도메인의 무거움**이었다.

| 검토했던 것 | 판정 |
|---|---|
| undo 배너 | ✗ 그냥 다시 고르면 된다 |
| 부분 취소 개념 | ✗ 선택 변경일 뿐이다 |
| 확인창 | ✗ 파괴적 행동이 아니다 |
| 취소 사유 묻기 | ✗ 물을 일이 없다 |
| **상대에게 알림** | **✓ 이것만 남는다** |

**A-16i는 독립 화면이 아니라 A-16으로 되돌아가는 것**이고, 상태 하나만 추가된다.
정작 자주 일어나는 것은 취소가 아니라 **매물 소진**(A-16j)이며, 그쪽이 이미 만든
A-16e를 재사용한다.
